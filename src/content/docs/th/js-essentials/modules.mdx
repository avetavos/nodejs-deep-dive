## สองระบบ Module

Node.js รองรับสองระบบ module ที่ไม่สามารถผสมกันได้อย่างอิสระ:

| ฟีเจอร์ | ESM | CommonJS |
|---------|-----|----------|
| Syntax | `import` / `export` | `require()` / `module.exports` |
| นามสกุลไฟล์ | `.mjs` หรือ `.js` พร้อม `"type":"module"` | `.cjs` หรือ `.js` ไม่มี `"type":"module"` |
| การโหลด | Static วิเคราะห์เมื่อ parse | Dynamic รันเมื่อ runtime |
| Top-level `await` | รองรับ | ไม่รองรับ |
| Default ใน Node 24+ | ใช่ เมื่อมี `"type": "module"` — และ CJS ก็ `require()` ได้ | Legacy default |

## CommonJS (CJS)

CommonJS คือระบบ module ดั้งเดิมของ Node.js ยังคงใช้กันอย่างแพร่หลายใน packages และ tooling เก่า

```js
// @skip-verify multi-file: illustrative
// math.js (CommonJS)
function add(a, b) { return a + b; }
function multiply(a, b) { return a * b; }

module.exports = { add, multiply };      // named exports via object
// OR: module.exports = add;             // single default export

// main.js (CommonJS)
const { add, multiply } = require('./math');
console.log(add(2, 3));       // 5
console.log(multiply(4, 5));  // 20
```

`require()` เป็น synchronous และโหลดไฟล์ทันทีเมื่อบรรทัดนั้นถูก execute ซึ่งหมายความว่าสามารถ `require()` ภายใน `if` block หรือฟังก์ชันได้

## ECMAScript Modules (ESM)

ESM คือมาตรฐาน JavaScript module อย่างเป็นทางการ ตอนนี้เป็นระบบที่แนะนำสำหรับ Node.js projects ใหม่

```js
// @skip-verify multi-file: illustrative
// math.mjs (ESM — named exports)
export function add(a, b) { return a + b; }
export function multiply(a, b) { return a * b; }

// utils.mjs (ESM — default export)
export default function formatNumber(n) {
  return n.toFixed(2);
}

// main.mjs (ESM — named import)
import { add, multiply } from './math.mjs';
import formatNumber from './utils.mjs';

console.log(add(2, 3));            // 5
console.log(formatNumber(3.14159)); // '3.14'
```

`import` statements เป็น **static** — ต้องปรากฏที่ด้านบนของไฟล์และถูก resolve ก่อนโค้ดใดๆ รัน ทำให้ bundlers สามารถทำ tree-shaking (การกำจัด dead-code) ได้

## การเปิดใช้งาน ESM ใน Node.js

สองวิธีในการบอก Node.js ว่าไฟล์ใช้ ESM:

1. **`"type": "module"` ใน `package.json`** — ไฟล์ `.js` ทั้งหมดใน package นั้นถือเป็น ESM ใช้ `.cjs` สำหรับไฟล์ใดๆ ที่ต้องคงเป็น CommonJS
2. **นามสกุล `.mjs`** — ถือเป็น ESM เสมอไม่ว่า `package.json` จะเป็นอะไร

```json
{
  "name": "my-app",
  "type": "module"
}
```

## Named vs Default Exports

```js
// @skip-verify multi-file: illustrative
// Named: export multiple bindings, import with exact names (or rename)
export const PI = 3.14159;
export function area(r) { return PI * r * r; }

import { PI, area } from './circle.mjs';
import { area as circleArea } from './circle.mjs'; // rename

// Default: one main export per file, imported with any name
export default class Logger { /* ... */ }

import Logger from './logger.mjs';
import MyLogger from './logger.mjs'; // same thing, different local name
```

## Demo ESM ที่รันได้

snippet นี้รันบน Node.js runtime (module resolution ต้องการ Node) แสดงการทำงานของ ES module ที่มี named exports end-to-end โดยใช้ inline dynamic `import()`

```js
// ESM inline via data: URL — requires Node runtime
const src = `
  export function add(a, b) { return a + b; }
  export const VERSION = '1.0.0';
`;
const mod = await import('data:text/javascript,' + encodeURIComponent(src));
console.log('add(3, 4):', mod.add(3, 4));
console.log('VERSION:', mod.VERSION);
```

export const modulesCode = `
// Dynamic import of an inline ESM module via data: URL
const src = [
  'export function add(a, b) { return a + b; }',
  'export const VERSION = "1.0.0";',
].join('\\n');

import('data:text/javascript,' + encodeURIComponent(src)).then(function(mod) {
  console.log('add(3, 4):', mod.add(3, 4));
  console.log('VERSION:', mod.VERSION);
  console.log('module keys:', Object.keys(mod).filter(function(k) { return k !== 'default'; }).join(', '));
});
`;

## Cheat sheet การ interop ระหว่าง CJS/ESM

codebase Node.js จริงผสม package CommonJS เก่ากับโค้ด ESM ใหม่อยู่ตลอด ดังนั้นกฎ interop มีผลแม้ในโปรเจกต์ "ESM ล้วน" ทันทีที่มัน depend package เก่าตัวหนึ่ง รายละเอียดเต็ม — รวมถึง module resolution algorithm และ `exports` map — อยู่ที่ [Module Resolution](/nodejs/th/modules-npm/resolution/) นี่คือ cheat sheet สำหรับสิ่งที่คุณจะเจอจริงๆ ตอนเขียนโค้ด application

| คำถาม | คำตอบบน Node 24 |
|---|---|
| CJS `require()` ไฟล์ ESM ได้ไหม? | ได้ โดย default — **ยกเว้น** ไฟล์ ESM นั้นใช้ top-level `await` ซึ่งจะ throw `ERR_REQUIRE_ASYNC_MODULE` |
| `__dirname` มีอยู่ในไฟล์ ESM ไหม? | ไม่มี — การอ้างถึงมันจะ throw `ReferenceError` ใช้ `import.meta.dirname` แทน |
| `import` binding อัปเดตตามเมื่อ module ต้นทาง reassign ใหม่ไหม? | ใช่ — ESM import เป็น **live binding** ไม่ใช่ copy |
| ค่าที่ destructure จาก `require()` อัปเดตแบบเดียวกันไหม? | ไม่ — CJS ให้ snapshot ของค่า ณ ตอนที่ `require()` รัน |
| `import x from './cjs-file.cjs'` เห็นอะไรเมื่อ `module.exports = someValue`? | `someValue` ในฐานะ **default** export |
| ไฟล์ `.js` ธรรมดาต้องมี `"type": "module"` เพื่อใช้ `import`/`export` ไหม? | บน Node 24, Node สามารถ auto-detect syntax ของ ESM และรันไฟล์เป็น module ได้แม้ไม่มี field นี้ (`detect-module`) — แต่ `"type"` ที่ระบุชัดเจนยังเป็นตัวเลือกที่ชัดเจนและ resolve เร็วกว่า |

export const requireEsmCode = `
const fs = require('node:fs');
const path = require('node:path');

const syncEsmPath = path.join(__dirname, 'sync-sibling.mjs');
const asyncEsmPath = path.join(__dirname, 'async-sibling.mjs');
fs.writeFileSync(syncEsmPath, "export function add(a, b) { return a + b; }\\nexport const VERSION = '1.0.0';\\n");
fs.writeFileSync(asyncEsmPath, "await new Promise((r) => setTimeout(r, 0));\\nexport const value = 42;\\n");

try {
  // require() of a synchronous ESM file works by default on Node 24
  const esm = require(syncEsmPath);
  console.log('require(sync esm).add(2,3):', esm.add(2, 3));

  // require() of an ESM file with top-level await cannot work synchronously
  try {
    require(asyncEsmPath);
  } catch (e) {
    console.log('require(async esm) threw:', e.code);
  }
} finally {
  fs.unlinkSync(syncEsmPath);
  fs.unlinkSync(asyncEsmPath);
}
`;

export const liveBindingCode = `
const fs = require('node:fs');
const path = require('node:path');
const { pathToFileURL } = require('node:url');

const esmCounterPath = path.join(__dirname, 'counter.mjs');
const cjsCounterPath = path.join(__dirname, 'counter.cjs');
const cjsDefaultPath = path.join(__dirname, 'greeter.cjs');

fs.writeFileSync(esmCounterPath, 'export let counter = 0;\\nexport function inc() { counter++; }\\n');
fs.writeFileSync(cjsCounterPath, 'let counter = 0;\\nfunction inc() { counter++; }\\nmodule.exports = { counter, inc };\\n');
fs.writeFileSync(cjsDefaultPath, "module.exports = function Greeter(name) { return 'Hi, ' + name; };\\n");

(async () => {
  try {
    // ESM import: the namespace object's property is a LIVE binding
    const esmNs = await import(pathToFileURL(esmCounterPath).href);
    console.log('esm import counter before inc():', esmNs.counter);
    esmNs.inc();
    console.log('esm import counter after inc():', esmNs.counter);

    // CJS require + destructure: a snapshot COPY taken at require() time
    const { counter, inc } = require(cjsCounterPath);
    console.log('cjs require counter before inc():', counter);
    inc();
    console.log('cjs require counter after inc() (still the old copy):', counter);

    // module.exports = <function> seen from the importing side as the default export
    const greeterNs = await import(pathToFileURL(cjsDefaultPath).href);
    console.log('cjs module.exports as import default:', greeterNs.default('Dana'));
  } finally {
    fs.unlinkSync(esmCounterPath);
    fs.unlinkSync(cjsCounterPath);
    fs.unlinkSync(cjsDefaultPath);
  }
})();
`;

export const liveBindingOut = `esm import counter before inc(): 0
esm import counter after inc(): 1
cjs require counter before inc(): 0
cjs require counter after inc() (still the old copy): 0
cjs module.exports as import default: Hi, Dana`;

## Mental Model

ให้นึกภาพ CJS และ ESM เป็นระบบไปรษณีย์สองระบบที่ส่งไปที่ mailbox เดียวกัน (ไฟล์บนดิสก์) CJS ส่ง **snapshot ที่ปิดผนึกแล้ว** — ไม่ว่า `module.exports` จะหน้าตาอย่างไรตอนที่ `require()` รัน มันถูก copy ออกมา; ไม่มีอะไรที่มาทีหลังอัปเดตมันได้ ESM ส่ง **สายไฟที่มีชีวิต** ไปยังตัวแปรจริงของ module ต้นทาง — `import { x } from './m.js'` binding ไม่ใช่ copy ของ `x` มันคือ view แบบ read-only ไปยัง `x` จริงของฝั่ง export ซึ่งเป็นเหตุผลที่มันอัปเดตตามฝั่ง export `__dirname` และ `import.meta.dirname` เป็นสองระบบที่ต่างกันสำหรับคำถามพื้นฐานเดียวกัน ("ไฟล์นี้อยู่ folder ไหน") และมีแค่ระบบของ ESM เท่านั้นที่สะกดว่า `import.meta.dirname`

## Trade-offs

| Choice | Benefit | Cost |
|---|---|---|
| CommonJS (`require`) | เรียบง่าย, synchronous, dynamic (`require()` ใน `if` ได้); package Node ที่มีอยู่เดิมทุกตัวยังใช้ได้ | ไม่มี top-level `await`; export แบบ snapshot ไม่ live; ต้องใช้เทคนิค `createRequire` สำหรับฟีเจอร์ที่มีแค่ใน `import.meta` |
| ESM (`import`/`export`) | ระบบ module มาตรฐานของ JS; static analysis และ tree-shaking; live binding; top-level `await` | `require()` ไฟล์ ESM ที่มี top-level `await` ไม่ได้; `__dirname`/`__filename` ไม่มีอยู่ |
| `"type": "module"` ใน `package.json` | ชัดเจน เร็ว — Node ไม่ต้อง sniff เนื้อหาไฟล์ | ไฟล์ `.js` ทุกไฟล์ใน package นั้นต้องเป็น ESM ที่ถูกต้อง (ใช้ `.cjs` สำหรับข้อยกเว้น) |
| พึ่งพา `detect-module` (ไม่มี field `"type"`) | ใช้ได้กับไฟล์ `.js` ที่กำกวมในวันนี้ | resolve ช้ากว่า (Node ต้องตรวจ syntax) และไม่ชัดเจนกับผู้อ่านว่าไฟล์นี้ใช้ระบบ module ไหน |

## Common Misconceptions

- **"`require()` ไฟล์ ESM ไม่ได้เลย"** โดยส่วนใหญ่ทำได้ — ข้อยกเว้นคือไฟล์ ESM ที่ใช้ top-level `await` โดยเฉพาะ ซึ่ง throw `ERR_REQUIRE_ASYNC_MODULE` เพราะ `require()` ต้อง return แบบ synchronous
- **"`__dirname` เป็น `undefined` ใน ES module"** มันไม่มีอยู่เลย — การอ้างถึงมัน throw `ReferenceError` ไม่ใช่ "ให้ `undefined`" ตัวแทนโดยตรงคือ `import.meta.dirname`
- **"การ import CommonJS module จาก ESM ก็ได้ live binding เหมือนกัน"** ไม่ — CJS module ไม่มี live binding เลยไม่ว่าฝั่งไหน Live binding เป็นฟีเจอร์เฉพาะของ ESM-to-ESM เท่านั้น การ import CJS จาก ESM ยังได้ snapshot ครั้งเดียว (ห่อให้ `module.exports` ปรากฏเป็น `default`)
