## ทำไม Buffer ถึงมีอยู่

JavaScript string ถูกเก็บภายในเป็น **UTF-16** — สองไบต์ต่อหนึ่ง code point ใน Basic Multilingual Plane นั่นก็โอเคสำหรับข้อความ แต่งาน networking และ filesystem ต้องจัดการกับ byte ดิบ: TCP packet, ภาพ JPEG หรือ binary protocol frame ไม่มี encoding โดยธรรมชาติ

`Buffer` คือคำตอบของ Node: ลำดับ byte ที่มีความยาวคงที่ ถูก expose เป็น subclass ของ Uint8Array มันมีมาก่อน typed array และยังเป็น type มาตรฐานที่คุณจะเห็นตลอดใน stream, HTTP, crypto และ fs API ของ Node

<Callout title="String เป็น UTF-16 ใน JS; Buffer จัดการ byte ดิบ">
JavaScript `string` ที่มี 4 ตัวอักษรอาจใช้พื้นที่ 4, 8 หรือมากกว่านั้นเป็นไบต์ ขึ้นอยู่กับ encoding `Buffer` แยกแนวคิดของ "กี่ตัวอักษร" ออกจาก "กี่ไบต์บนสาย" ให้ใช้ `Buffer.byteLength(str, encoding)` เสมอ — ไม่ใช่ `str.length` — เมื่อต้องการขนาดไบต์ของ string
</Callout>

## การสร้าง Buffer

วิธีที่แนะนำคือ `Buffer.from()` constructor `new Buffer()` ถูก deprecate แล้ว (`DEP0005`) — มันยังทำงานได้และพิมพ์ `DeprecationWarning` แต่อย่าใช้ใน code ใหม่เด็ดขาด

export const bufferFromCode = `
// From a string (UTF-8 by default)
var buf1 = Buffer.from('Hello');
console.log('buf1:', buf1);           // <Buffer 48 65 6c 6c 6f>
console.log('buf1 length:', buf1.length); // 5 bytes

// From a hex string
var buf2 = Buffer.from('deadbeef', 'hex');
console.log('buf2:', buf2);           // <Buffer de ad be ef>
console.log('buf2 length:', buf2.length); // 4 bytes

// Allocate a zeroed buffer of N bytes
var buf3 = Buffer.alloc(4);
console.log('buf3 (zeroed):', buf3);  // <Buffer 00 00 00 00>
`;

## Buffer.alloc vs Buffer.allocUnsafe

`Buffer.alloc(size)` zero-fill หน่วยความจำก่อนส่งมอบให้คุณ — ปลอดภัย แต่เสียต้นทุนเขียนทับทุกไบต์ `Buffer.allocUnsafe(size)` ข้าม zero-fill นั้นไปและให้ byte ที่นั่งอยู่ในพื้นที่ memory pool นั้นอยู่แล้วมาให้คุณเลย — เร็วกว่า แต่ byte เหล่านั้นอาจเป็น **อะไรก็ได้** รวมถึงเศษข้อมูลที่หลงเหลือจาก buffer ที่ถูกปล่อยไปก่อนหน้านี้ (request body เก่า, เนื้อหาไฟล์เก่า, ความลับเก่า)

<Callout title="allocUnsafe ปลอดภัยก็ต่อเมื่อคุณเขียนทับทุกไบต์ก่อนอ่านมัน">
`allocUnsafe` เป็นกับดักตัวจริงใน AI-generated code: มันหน้าตาเหมือน `alloc` เป๊ะใน diff รันได้ปกติในเครื่อง local (pool มักจะถูก zero อยู่แล้วบน process ใหม่) แล้วก็รั่วไหลข้อมูล heap เก่าใน production เมื่อ pool ถูกนำกลับมาใช้ใหม่ ใช้มันเฉพาะตอนที่คุณกำลังจะ `.fill()` หรือเขียนทับทุกไบต์เองทันที (เช่น เป็น scratch buffer ที่ส่งตรงไปยัง `fs.read()`)
</Callout>

export const bufferAllocUnsafeCode = `
var safe = Buffer.alloc(8);
console.log('alloc(8):', safe); // always zeroed — deterministic

var unsafe = Buffer.allocUnsafe(8);
console.log('allocUnsafe(8) length:', unsafe.length);
console.log('allocUnsafe(8) is a Buffer:', Buffer.isBuffer(unsafe));
// unsafe's contents are NOT printed here — they are whatever bytes were
// already in that memory region and are not guaranteed to be the same
// from one run (or one machine) to the next.

// The safe pattern: fill or fully overwrite before use
unsafe.fill(0);
console.log('after fill(0):', unsafe);
console.log('now equal to alloc(8):', unsafe.equals(safe));
`;

export const bufferAllocUnsafeOut = `alloc(8): <Buffer 00 00 00 00 00 00 00 00>
allocUnsafe(8) length: 8
allocUnsafe(8) is a Buffer: true
after fill(0): <Buffer 00 00 00 00 00 00 00 00>
now equal to alloc(8): true`;

ตัวอย่างประกอบเท่านั้น — byte จริงด้านล่างจะแตกต่างกันทุกครั้งที่รัน ซึ่งนั่นคือประเด็นทั้งหมด:

## base64url — encoding ที่ปลอดภัยสำหรับ URL/cookie/header

base64 มาตรฐานอาจมี `+`, `/` และ padding `=` ต่อท้าย — ทั้งสามตัวต้อง escape ใน URL, cookie หรือ HTTP header `base64url` (Node 15.7+) คือ encoding เดียวกันแต่ใช้ alphabet ที่ปลอดภัยสำหรับ URL (`-`/`_` แทน `+`/`/`) และไม่มี padding ซึ่งเป็น format เดียวกับที่ JWT ใช้สำหรับส่วน header และ payload

export const base64urlCode = `
function b64url(obj) {
  return Buffer.from(JSON.stringify(obj)).toString('base64url');
}

// A JWT-shaped payload: header.payload (signature omitted for this demo)
var header = b64url({ alg: 'HS256', typ: 'JWT' });
var payload = b64url({ sub: '1234567890', name: 'Ada' });
console.log('header:', header);
console.log('payload:', payload);
console.log('token:', header + '.' + payload + '.SIGNATURE');

// base64url is safe to drop straight into a URL, cookie, or header value —
// it never produces +, /, or trailing = padding.
var raw = Buffer.from([0xff, 0xff, 0xbe]);
console.log('standard base64:', raw.toString('base64')); // contains + and /
console.log('base64url      :', raw.toString('base64url')); // - and _ instead, no padding

// Round-trip
var decoded = JSON.parse(Buffer.from(payload, 'base64url').toString('utf8'));
console.log('decoded payload:', decoded);
`;

export const base64urlOut = `header: eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9
payload: eyJzdWIiOiIxMjM0NTY3ODkwIiwibmFtZSI6IkFkYSJ9
token: eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJzdWIiOiIxMjM0NTY3ODkwIiwibmFtZSI6IkFkYSJ9.SIGNATURE
standard base64: //++
base64url      : __--

## การ Slice และ copy

`buf.slice(start, end)` (หรือ `buf.subarray`) คืนค่า view ของ memory เดียวกัน — แก้ไข slice ก็แก้ไขต้นฉบับด้วย ใช้ `Buffer.from(slice)` เพื่อได้ copy อิสระ

export const sliceCode = `
var buf = Buffer.from('Hello, World!');
var slice = buf.slice(0, 5);
console.log('slice:', slice.toString()); // Hello

// slice shares memory — mutating it mutates buf
slice[0] = 0x4A; // 'J'
console.log('buf after mutation:', buf.toString()); // Jello, World!

// Independent copy
var copy = Buffer.from(buf.slice(7, 12));
copy[0] = 0x77; // 'w'
console.log('copy:', copy.toString());   // world
console.log('buf unchanged:', buf.toString());
`;

export const sliceOut = `slice: Hello
buf after mutation: Jello, World!
copy: world
buf unchanged: Jello, World!`;

## StringDecoder: ถอดรหัสตัวอักษร multi-byte ที่ถูกตัดข้าม chunk

network stream ส่งมอบ byte เป็น chunk ตามที่ OS หยิบยื่นมาให้ — มันไม่รู้เลยว่าขอบเขตของตัวอักษร UTF-8 อยู่ตรงไหน ถ้าตัวอักษร multi-byte (เช่นตัวอักษรไทยส่วนใหญ่ที่ใช้ 3 ไบต์ต่อตัวใน UTF-8) ถูกตัดข้ามสอง chunk การเรียก `.toString('utf8')` บนแต่ละ chunk **แยกกัน** จะทำให้มันเสียหาย: แต่ละครึ่งเป็น byte sequence ที่ไม่สมบูรณ์ ทั้งสองครึ่งจึงถอดรหัสออกมาเป็นตัวอักษรทดแทนของ Unicode (`�`)

`StringDecoder` จาก `node:string_decoder` แก้ปัญหานี้: มัน buffer ไบต์ที่ตกค้างไม่สมบูรณ์และต่อเข้ากับ chunk ถัดไป ทำให้ตัวอักษร multi-byte จะถูกถอดรหัสก็ต่อเมื่อมันสมบูรณ์แล้วเท่านั้น

export const stringDecoderCode = `
const { StringDecoder } = require('node:string_decoder');

var thai = 'สวัสดี'; // 6 Thai characters
var full = Buffer.from(thai, 'utf8');
console.log('full string:', thai);
console.log('total bytes:', full.length);

// Split the buffer mid-character to simulate a chunk boundary landing
// inside a multi-byte sequence, as can happen with any network stream.
var splitAt = 4;
var chunk1 = full.subarray(0, splitAt);
var chunk2 = full.subarray(splitAt);

console.log('--- naive: toString() per chunk ---');
console.log('chunk1.toString():', JSON.stringify(chunk1.toString('utf8')));
console.log('chunk2.toString():', JSON.stringify(chunk2.toString('utf8')));
console.log('naive concat:', chunk1.toString('utf8') + chunk2.toString('utf8'));

console.log('--- correct: StringDecoder buffers partial characters ---');
var decoder = new StringDecoder('utf8');
var result = decoder.write(chunk1);
result += decoder.write(chunk2);
result += decoder.end();
console.log('decoded:', result);
console.log('matches original:', result === thai);
`;

export const stringDecoderOut = `full string: สวัสดี
total bytes: 18
--- naive: toString() per chunk ---
chunk1.toString(): "ส�"
chunk2.toString(): "��ัสดี"
naive concat: ส���ัสดี
--- correct: StringDecoder buffers partial characters ---
decoded: สวัสดี
matches original: true`;

## Trade-offs

| ทางเลือก | ข้อดี | ต้นทุน |
|---|---|---|
| `Buffer.alloc(n)` | ปลอดภัยเสมอ — memory ที่ zero แบบ deterministic | เสียต้นทุน zero-fill แม้ว่าคุณกำลังจะเขียนทับทุกอย่างอยู่แล้วก็ตาม |
| `Buffer.allocUnsafe(n)` | ข้าม zero-fill — เร็วกว่าใน hot path | เนื้อหายังไม่ถูกกำหนดจนกว่าคุณจะเขียนทับ; ลืมทำแล้วรั่วไหลข้อมูล heap เก่า |
| view จาก `.slice()`/`.subarray()` | zero-copy — ไม่มีการจอง memory ใหม่ | แก้ไข view ก็แก้ไข buffer ต้นฉบับด้วย ซึ่งพลาดได้ง่ายโดยไม่ตั้งใจ |
| `.toString()` ต่อ chunk | code ง่ายที่สุดเท่าที่จะทำได้ | ทำให้ตัวอักษร multi-byte ที่ถูกตัดข้าม chunk เสียหายแบบเงียบ ๆ |
| `StringDecoder` | ถูกต้องข้ามขอบเขต chunk | มี object เพิ่มอีกหนึ่งตัวที่ต้องพกไปกับ code จัดการ stream ของคุณ |

## Common Misconceptions

- **"`Buffer.allocUnsafe` ก็แค่ `Buffer.alloc` ที่เร็วกว่า"** — ความจริง: มันเร็วกว่าเพราะข้ามการ zero memory; byte ที่ได้กลับมาคือข้อมูลที่หลงเหลืออยู่ ไม่ใช่ zero จนกว่าคุณจะเขียนทับมันเอง
- **"base64 กับ base64url คือสิ่งเดียวกันแค่ชื่อต่างกัน"** — ความจริง: base64url แทน `-`/`_` ด้วย `+`/`/` และตัด padding ออก โดยเฉพาะเพื่อให้ผลลัพธ์ปลอดภัยสำหรับฝังใน URL, cookie หรือ header โดยไม่ต้อง escape
- **"`chunk.toString('utf8')` ปลอดภัยเสมอสำหรับ text stream"** — ความจริง: มันปลอดภัยก็ต่อเมื่อขอบเขต chunk ไม่เคยตัดตัวอักษร multi-byte — ซึ่ง network stream ไม่สามารถรับประกันได้
- **"`buf.slice()` คืนค่า copy เหมือน `Array.prototype.slice()`"** — ความจริง: `Buffer#slice`/`#subarray` คืนค่า **view** เหนือ memory เดียวกัน; แก้ไข slice ก็แก้ไขต้นฉบับด้วย

## อ่านโค้ดที่ AI เขียน

- `Buffer.allocUnsafe()` ถูกใช้ในที่ที่ buffer ถูกอ่าน (log, ส่งออก, hash) ก่อนที่ทุกไบต์จะถูกเขียนหรือ `.fill()` อย่างชัดเจนหรือเปล่า?
- stream handler เรียก `chunk.toString('utf8')` บนแต่ละ chunk แยกกัน แทนที่จะสะสมด้วย `Buffer.concat()` หรือถอดรหัสด้วย `StringDecoder` หรือเปล่า? แบบนี้จะพังทันทีที่ตัวอักษร multi-byte (ไทย, emoji, CJK) คร่อมขอบเขต chunk
- code คำนวณขนาด string ด้วย `str.length` แทนที่จะเป็น `Buffer.byteLength(str, 'utf8')` ก่อนจอง buffer ขนาดคงที่หรือตั้งค่า header `Content-Length` หรือเปล่า? input ที่ไม่ใช่ ASCII จะล้นหรือถูกตัดทอน
- JWT หรือ URL token ถูกสร้างด้วย `base64` มาตรฐานแทนที่จะเป็น `base64url` ซึ่งต้อง escape `+`/`/`/`=` ด้วยมือและพลาดง่ายหรือเปล่า?

</Callout>
