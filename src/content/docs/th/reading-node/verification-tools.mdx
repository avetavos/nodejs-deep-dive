## ขั้นที่ 1: `node --test` พร้อม coverage

## ขั้นที่ 2: `--trace-warnings`, `--unhandled-rejections=strict`, `--trace-uncaught`

`--trace-warnings` เปลี่ยน warning เปล่า ๆ ให้กลายเป็น stack trace เต็มที่ชี้ไปยังจุดที่ปัญหาถูกสร้างขึ้นจริง รันกับ pattern listener leak จาก *AI bug catalog*:

```text
listener count: 11
(node:45399) MaxListenersExceededWarning: Possible EventEmitter memory leak detected. 11 data listeners added to [EventEmitter]. MaxListeners is 10. Use emitter.setMaxListeners() to increase limit
    at genericNodeError (node:internal/errors:985:15)
    at wrappedFn (node:internal/errors:539:14)
    at _addListener (node:events:582:17)
    at EventEmitter.addListener (node:events:600:10)
    at handleRequest (file:///.../listener-leak.mjs:10:11)
    at file:///.../listener-leak.mjs:13:30
warning name: MaxListenersExceededWarning
```

ถ้าไม่มี flag นี้ warning ก็ยัง print อยู่ — แค่ไม่มี stack เหลือแค่ "listener นี้ถูกเพิ่มที่ไหนจริง ๆ" เป็นการค้นหาด้วยมือทั่วทั้ง codebase แทนที่จะเป็นเลขบรรทัดที่ชัดเจน

`--unhandled-rejections=strict` เป็นพฤติกรรม *ดีฟอลต์* มาตั้งแต่ Node 15 — รันแบบระบุ flag ตรง ๆ กับ pattern floating promise ให้ผล crash เดียวกันไม่ว่าจะมี flag หรือไม่:

```text
save queued
Error: missing id
    at saveRecord (...)
Node.js v24.13.0
```

flag นี้มีความหมายสำหรับโค้ดที่ยังรันบน Node เวอร์ชันเก่ามาก ๆ หรือ codebase ที่จงใจ override ค่าดีฟอลต์กลับไปเป็น `warn` — บน Node 24.13 ปัจจุบัน การ crash เกิดขึ้นเหมือนกันไม่ว่าจะมี flag หรือไม่

`--trace-uncaught` เพิ่มอีกหนึ่งส่วน `Thrown at:` เข้าไปบน output ดีฟอลต์ของ uncaught exception ใน Node — ชี้ไปยังบรรทัดที่ error ถูก throw จริง แยกจากจุดที่มันถูก catch (หรือไม่ถูก catch) ขึ้นไปใน stack กับ pattern event `error` ที่ไม่มี listener output ดีฟอลต์ก็แสดง `Emitted 'error' event at:` อยู่แล้ว `--trace-uncaught` เพิ่ม block `Thrown at:` ที่สองเข้ามาด้วยตำแหน่งเดียวกันสำหรับกรณีง่าย ๆ นี้ แต่ทั้งสองอาจต่างกันได้ในโค้ดที่ error ถูก throw ที่หนึ่งแล้วโผล่ขึ้นไปถึง top level ที่อีกจุดหนึ่งไปเลย

## ขั้นที่ 3: `eslint-plugin-n` + `eslint-plugin-promise` รันจริง

ติดตั้งในโปรเจกต์ scratch: `eslint@9.39.5`, `eslint-plugin-n@18.3.0`, `eslint-plugin-promise@7.3.0` flat config โดยใช้ flat preset ที่แต่ละ plugin export มาเอง:

```js
// @skip-verify eslint config, not a runnable program
import n from 'eslint-plugin-n';
import promise from 'eslint-plugin-promise';

export default [
  n.configs['flat/recommended-module'],
  promise.configs['flat/recommended'],
  {
    rules: {
      'no-eval': 'error',
    },
  },
];
```

รันกับไฟล์เป้าหมายที่สร้างขึ้นเพื่อรวม pattern จาก *AI bug catalog* หลายตัวไว้ด้วยกัน:

```js
// @expect-throw
import fs from 'node:fs';

const data = fs.readFileSync('/etc/hosts');

function fetchUser(id) {
  return new Promise(function (ok, bad) {
    ok({ id: id });
  });
}

function handleUser(id) {
  fetchUser(id).then(function (user) {
    console.log(user);
  });
}

function chained(id) {
  return fetchUser(id).then(function (user) {
    fetchUser(user.id + 1).then(function (next) {
      console.log(next);
    });
  });
}

handleUser(1);
chained(2);

eval('console.log(1)');

process.exit(1);

new Buffer(10);
```

## ขั้นที่ 6: `knip` (unused exports)

กับ package scratch สองไฟล์ที่ `math.js` export `add`, `subtract`, และ `multiply` แต่มีแค่ `add` เท่านั้นที่ถูก import ใช้จริง:

```text
Unused exports (2)
subtract  function  src/math.js:5:17
multiply  function  src/math.js:9:17
```

`knip` หาสิ่งนี้ได้จากการตาม import graph จริง ไม่ใช่การจับคู่ข้อความ — เป็นเครื่องมือตัวเดียวใน ladder นี้ที่ตอบคำถามที่ 24 pattern ในแคตตาล็อกไม่ได้พูดถึงจริง ๆ ("โค้ดนี้ถูกเรียกถึงได้หรือไม่") แทนที่จะเป็น "โค้ดที่ถูกเรียกถึงได้นี้ถูกต้องหรือไม่"

## ตาราง pattern-to-rung

| # | Pattern | ขั้นที่จับได้ |
|---|---|---|
| 1 | ลืม `await` | ไม่มี — ต้องใช้คนเท่านั้น |
| 2 | `forEach(async ...)` | ไม่มี — ต้องใช้คนเท่านั้น |
| 3 | Floating promise / unhandled rejection | `promise/catch-or-return` ของ `eslint-plugin-promise`; ตัว crash เป็นดีฟอลต์ของ Node เอง |
| 4 | `Promise.all` ไม่จำกัด concurrency | ไม่มี — ต้องใช้คนเท่านั้น (เปิดเผยได้ด้วย autocannon/load จริง) |
| 5 | `setTimeout(fn, 0)` เทียบกับ `setImmediate`/`nextTick` | ไม่มี — ต้องใช้คนเท่านั้น |
| 6 | งาน CPU แบบ synchronous ใน handler | ไม่มี — ต้องใช้คนเท่านั้น (เปิดเผยได้ด้วย `--cpu-prof`/`monitorEventLoopDelay`) |
| 7 | `res.end()` เรียกสองครั้ง | ไม่มี — ต้องใช้คนเท่านั้น |
| 8 | ตั้ง header หลังส่ง response แล้ว | ไม่มี — ต้องใช้คนเท่านั้น |
| 9 | ไม่จำกัดขนาด request body | ไม่มี — ต้องใช้คนเท่านั้น (เปิดเผยได้ด้วย autocannon) |
| 10 | `JSON.parse` ไม่มี `try`/`catch` | ไม่มี — ต้องใช้คนเท่านั้น |
| 11 | `fetch` ไม่เช็ก `.ok`/timeout | ไม่มี — ต้องใช้คนเท่านั้น |
| 12 | Listener leak | `--trace-warnings` |
| 13 | event `error` ไม่มี listener | ไม่มี — ต้องใช้คนเท่านั้น |
| 14 | `.pipe()` ไม่มีการจัดการ error | ไม่มี — ต้องใช้คนเท่านั้น |
| 15 | decode string ข้าม chunk boundary | ไม่มี — ต้องใช้คนเท่านั้น |
| 16 | `Buffer.concat` ข้างใน loop | ไม่มี — ต้องใช้คนเท่านั้น (เปิดเผยได้ด้วย `--cpu-prof`) |
| 17 | `process.env.PORT` ถูกเทียบเป็น string | ไม่มี — ต้องใช้คนเท่านั้น |
| 18 | `process.exit()` กลางงานที่ยังค้าง | ไม่มี — ต้องใช้คนเท่านั้น |
| 19 | ปน `require`/`import`, `__dirname` ใน ESM | ไม่มี — ต้องใช้คนเท่านั้น (runtime error เกิดขึ้นทันที) |
| 20 | `^0.x`, ไม่มี lockfile, `npm install` ใน Docker | `npm audit`/`npm ci` จับความคลาดเคลื่อนที่เกี่ยวข้องได้ ไม่ใช่ตัวเลือก Dockerfile เอง |
| 21 | ลำดับ field `exports` ผิด | ไม่มี — ต้องใช้คนเท่านั้น |
| 22 | ไม่มี assertion / mock ผิดที่ / test ใช้ timer จริง | `node --test` เมื่อมี assertion จริงและ mock ถูกใช้ในตำแหน่งที่ถูกต้อง |
| 23 | `console.log` แทน structured log | ไม่มี — ต้องใช้คนเท่านั้น |
| 24 | `exec`/`eval` injection | ไม่มี — ต้องใช้คนเท่านั้น (`npm audit`/`osv-scanner` จับ *dependency* ที่มีช่องโหว่ ไม่ใช่สิ่งนี้) |

## คำสั่งเดียวสำหรับทั้ง ladder

```bash
node --test --experimental-test-coverage && \
  NODE_OPTIONS="--trace-warnings --unhandled-rejections=strict" node --test && \
  npx eslint . && \
  npm audit --audit-level=high
```

สี่ขั้นในบรรทัด shell เดียว เชื่อมด้วย `&&` ทำให้ล้มเหลวที่ขั้นไหนก็หยุดที่เหลือทันที — `--cpu-prof`/`autocannon` และ `knip` ถูกตั้งใจไม่รวมไว้ใน one-liner นี้ เพราะต้องมี server ที่รันอยู่จริงและ import graph เต็ม ๆ ตามลำดับ ไม่ใช่แค่ source tree ให้ lint และ test

## Mental Model

ทุกขั้นใน ladder นี้ตอบคำถามที่แคบและเฉพาะเจาะจง — โค้ดทำตามที่ test บอกไหม มีอะไร warn ไหม style สม่ำเสมอไหม dependency มีช่องโหว่ที่รู้จักไหม เร็วพอไหม มีอะไรเรียกไม่ถึงไหม — และไม่มีข้อไหนตอบว่า "โค้ดนี้ถูกต้องหรือไม่" ตัวเลขในตาราง pattern-to-rung เองก็ยืนยันสิ่งนี้ชัดเจน: 21 จาก 24 pattern ในแคตตาล็อกไม่มีขั้นอัตโนมัติจับได้เลย

## Trade-offs

| ทางเลือก | ประโยชน์ | ต้นทุน |
|---|---|---|
| รัน ladder เต็มทุก PR | จับ bug กลุ่มจริงแม้จะแคบได้อัตโนมัติทุกครั้ง | หกเครื่องมือแยกกัน หลายตัวต้องการ network/CI setup (`osv-scanner`, `autocannon` ที่ต้องมี server รันอยู่จริง) |
| รันแค่ `node --test` + eslint | เร็วพอสำหรับ pre-commit hook | พลาด dependency ที่มีช่องโหว่, โค้ดที่เรียกไม่ถึง, และ performance regression ไปเลย |
| ถือว่า ladder รันสะอาดแล้วแปลว่า "รีวิวแล้ว" | ไม่มี — นี่ไม่เคยเป็นข้อแลกเปลี่ยนที่ดี | ทุกเครื่องมือที่นี่แคบโดยการออกแบบ; run สะอาดพิสูจน์แค่ว่าสิ่งแคบ ๆ ที่มันเช็กนั้นโอเค |

## Common Misconceptions

- **"`--experimental-test-coverage` เป็น experimental แปลว่าเชื่อถือไม่ได้"** ชื่อ flag บอกว่ารูปแบบรายงานอาจยังเปลี่ยนได้ ไม่ได้บอกว่าตัวเลข coverage ที่มันแสดงวันนี้ผิด — มันมาจาก V8 coverage instrumentation จริง เป็น primitive เดียวกับที่เครื่องมือแบบ Istanbul สร้างต่อยอด
- **"`npm audit` กับ `osv-scanner` ซ้ำซ้อนกันเพราะเจอ advisory เดียวกันในตัวอย่างนี้"** ทั้งคู่อ่านฐานข้อมูลต่างกัน (advisory feed ของ npm เองเทียบกับ aggregator ของ OSV) และอาจต่างกันได้ในระบบนิเวศที่ไม่ใช่ npm หรือ advisory ที่เพิ่งออกมาไม่นาน — รันตัวใดตัวหนึ่งไม่ใช่สิ่งทดแทนอีกตัวสำหรับทุกโปรเจกต์
- **"load test ด้วย autocannon พิสูจน์ว่า server ไม่มี bug"** มันพิสูจน์แค่ว่า handler *ตัวนี้* รับ concurrency *นี้* และ payload รูปร่าง *นี้* ไหวบนเครื่อง *นี้* — ไม่ได้บอกอะไรเลยเกี่ยวกับ route อื่น, body ที่ใหญ่กว่า, หรือ handler ที่เป็น CPU-bound จริง ๆ

## อ่านโค้ดที่ AI เขียน

ก่อนจะเชื่อคำอ้างของ AI assistant ว่า "test ผ่านแล้ว" หรือ "lint สะอาดแล้ว" ให้ reproduce มันเอง: pattern 22 ของ *AI bug catalog* มีอยู่ก็เพราะ `node --test` ที่เขียวสามารถแปลว่า "ไม่มี assertion ที่เรียกถึงได้ตัวไหน fail" ไม่ใช่ "โค้ดนี้ถูกต้อง" รัน ladder จริงข้างบนกับ diff จริง อ่านชื่อกฎจริงใน output แล้วเช็กแต่ละจุดที่เจอกับตาราง pattern-to-rung ก่อนจะตัดสินว่าเครื่องมือ "จัดการ" เรื่องที่ตารางบอกว่ามันไม่ครอบคลุมแล้ว
