## ทำไมต้องวัด?

> "การ optimize ก่อนเวลาอันควรคือต้นตอของความชั่วทั้งปวง" — Donald Knuth

ก่อนที่คุณจะ optimize อะไรก็ตาม **ต้องวัดก่อนเสมอ** โมดูล `perf_hooks` ของ Node ให้การจับเวลาแบบ sub-millisecond ผ่าน High Resolution Time API — `performance.now()` เดียวกับที่คุณรู้จักจาก browser แต่ใช้ได้ใน Node แบบ native และ `PerformanceObserver` สำหรับการรับ entry แบบ async

## performance.now()

`performance.now()` คืนค่า float ในหน่วย **milliseconds** ที่มีความแม่นยำระดับ microsecond เป็น monotonic — ไม่เคยถอยหลัง แม้ระบบนาฬิกาจะถูกปรับ:

```js
import { performance } from 'node:perf_hooks';

const start = performance.now();

// --- work to measure ---
let sum = 0;
for (let i = 0; i < 1_000_000; i++) {
  sum += i;
}
// ----------------------

const elapsed = performance.now() - start;
console.log('Sum loop took: ' + elapsed.toFixed(3) + ' ms');
```

## performance.mark() และ performance.measure()

สำหรับการวัดที่มีชื่อและแสดงใน DevTools timelines:

```js
import { performance, PerformanceObserver } from 'node:perf_hooks';

performance.mark('db-start');
// ... simulate a DB query ...
await new Promise(function(resolve) { setTimeout(resolve, 50); });
performance.mark('db-end');

performance.measure('database-query', 'db-start', 'db-end');

const entries = performance.getEntriesByName('database-query');
console.log(entries[0].duration.toFixed(2) + ' ms');
```

## PerformanceObserver — การเก็บข้อมูลแบบ async

`PerformanceObserver` เรียก callback เมื่อมี performance entry ใหม่ถูกสร้างขึ้น มีประโยชน์สำหรับการวัด library code ที่คุณไม่ได้ควบคุม:

```js
import { PerformanceObserver, performance } from 'node:perf_hooks';

const obs = new PerformanceObserver(function(list) {
  for (const entry of list.getEntries()) {
    console.log(entry.name + ': ' + entry.duration.toFixed(2) + ' ms');
  }
});

obs.observe({ entryTypes: ['measure'] });

performance.mark('a');
// ... work ...
performance.mark('b');
performance.measure('my-operation', 'a', 'b');

// Always disconnect when done to avoid memory leaks
obs.disconnect();
```

`entryTypes` ไม่ได้จำกัดแค่ `'measure'` เท่านั้น entry ประเภท `'function'` มาจาก `performance.timerify()` ซึ่งห่อฟังก์ชันแล้วส่ง `PerformanceEntry` ทุกครั้งที่มันถูกเรียก — ไม่ต้องมีคู่ `mark`/`measure` เอง:

export const timerifyCode = `
import { PerformanceObserver, performance } from 'node:perf_hooks';

const obs = new PerformanceObserver((list) => {
  const names = list.getEntries().map((e) => e.entryType);
  console.log('observed entry types include function:', names.includes('function'));
  obs.disconnect();
});
obs.observe({ entryTypes: ['function'] });

const timed = performance.timerify(function slow(n) {
  let s = 0;
  for (let i = 0; i < n; i++) s += i;
  return s;
});
timed(100000);
`;

export const timerifyOut = `observed entry types include function: true`;

<NodeRunner client:visible code={timerifyCode} node expected={timerifyOut} />

entry ประเภท `'gc'` ต้องใช้ `--expose-gc` (เพื่อเรียก `global.gc()` ตามต้องการ) และสังเกตอัตโนมัติทุกครั้งที่มี garbage collection รอบจริงเกิดขึ้น — มีประโยชน์เวลาเชื่อมโยง latency ที่พุ่งขึ้นกับ GC pause:

```bash

```

```js
  console.log('gc entry seen:', list.getEntries().length > 0);
  obs.disconnect();
});

global.gc();
```

## วัด event loop lag ด้วย monitorEventLoopDelay

`performance.now()` วัดงานที่คุณรู้อยู่แล้วว่าจะวัด `monitorEventLoopDelay()` ตอบคำถามที่ต่างออกไป — "มีอะไรกำลังบล็อก loop อยู่ตอนนี้หรือเปล่า แม้แต่โค้ดที่คุณไม่ได้ควบคุม" — โดย sample ช่องว่างระหว่างรอบของ event loop:

export const eventLoopDelayCode = `
import { monitorEventLoopDelay } from 'node:perf_hooks';

const h = monitorEventLoopDelay({ resolution: 20 });
h.enable();

// Block the loop synchronously to create measurable delay.
const until = Date.now() + 100;
while (Date.now() < until) {}

setTimeout(() => {
  h.disable();
  console.log('saw event loop delay:', h.max > 0);
  console.log('min <= mean <= max:', h.min <= h.mean && h.mean <= h.max);
}, 50);
`;

export const eventLoopDelayOut = `saw event loop delay: true
min <= mean <= max: true`;

<NodeRunner client:visible code={eventLoopDelayCode} node expected={eventLoopDelayOut} />

`h.min`/`h.mean`/`h.max`/`h.percentile(N)` เป็นหน่วยนาโนวินาทีทั้งหมด production server ที่ expose `h.percentile(99)` ไว้บน endpoint สำหรับ health/metrics จะบอกคุณเกี่ยวกับ lag ที่เกิดจากงาน synchronous *ใดก็ตาม*ทั่วทั้ง process — โค้ดของคุณ, dependency, แม้แต่ native addon — ไม่ใช่แค่ช่วงที่คุณห่อด้วย `performance.mark()` เท่านั้น

## Demo แบบ Live — จับเวลา CPU-bound loop

export const perfCode = `
import { performance } from 'node:perf_hooks';

function fibonacci(n) {
  if (n <= 1) return n;
  return fibonacci(n - 1) + fibonacci(n - 2);
}

const iterations = [10, 20, 30, 35];

for (const n of iterations) {
  const t0 = performance.now();
  const result = fibonacci(n);
  const elapsed = performance.now() - t0;
  console.log('fib(' + n + ') = ' + result + '  [' + elapsed.toFixed(3) + ' ms]');
}
`;

## การรักษา event loop ไม่ให้ถูกบล็อก

CPU-bound loop ที่ทำงานนานกว่า ~50 ms จะ**บล็อก event loop** — ไม่มี I/O, ไม่มี timer, ไม่มี request อื่นที่ประมวลผลได้ในระหว่างนั้น

```js
// BAD — blocks the event loop for the entire duration
function blockingWork(data) {
  const result = [];
  for (const item of data) {
    result.push(expensiveTransform(item)); // each call takes ~1ms, 10000 items = 10s block
  }
  return result;
}

// BETTER — yield control periodically with setImmediate
async function nonBlockingWork(data) {
  const result = [];
  for (let i = 0; i < data.length; i++) {
    result.push(expensiveTransform(data[i]));
    if (i % 100 === 0) {
      // Yield to the event loop every 100 items
      await new Promise(function(resolve) { setImmediate(resolve); });
    }
  }
  return result;
}

// BEST for CPU-heavy work — offload to a Worker Thread (see below in this lesson)
import { Worker } from 'node:worker_threads';
```

## worker_threads สำหรับงานที่ใช้ CPU หนัก

การแบ่งงานด้วย `setImmediate` (ข้างบน) ทำให้ event loop ตอบสนองได้โดย*สลับ*งานนั้นกับงานอื่น — CPU time รวมที่ใช้เท่าเดิม แค่กระจายออกไป ส่วน `Worker` ย้ายงานไปยัง**เธรดอื่นจริง ๆ** ทำให้ main thread จัดการ I/O แบบขนานไปด้วยได้ แทนที่จะผลัดกันทำ:

export const workerCode = `
import { Worker, isMainThread, parentPort, workerData } from 'node:worker_threads';

function fib(n) { return n <= 1 ? n : fib(n - 1) + fib(n - 2); }

if (isMainThread) {
  const worker = new Worker(new URL(import.meta.url), { workerData: 30 });
  worker.on('message', (result) => {
    console.log('worker result:', result);
    console.log('main thread was free to do other work while this ran');
  });
} else {
  // This branch runs inside the worker thread, in the same file.
  const result = fib(workerData);
  parentPort.postMessage(result);
}
`;

export const workerOut = `worker result: 832040
main thread was free to do other work while this ran`;

<NodeRunner client:visible code={workerCode} node expected={workerOut} />

ไฟล์เดียวทำหน้าที่เป็นทั้ง entry point ของ main thread และ script ของ worker ได้ด้วยการแยก branch ตาม `isMainThread` — `new Worker(new URL(import.meta.url), ...)` รันไฟล์เดียวกันนี้ซ้ำในเธรดใหม่ และ `workerData`/`parentPort.postMessage()` คือช่องทางสื่อสารสองทิศทางเข้า-ออก สำหรับงานจริงให้แยก worker ไปเป็นไฟล์ของตัวเองเมื่อ logic เริ่มยาวเกินไม่กี่บรรทัด

<Callout title="Worker มี overhead — ใช้กับงาน CPU จริง ไม่ใช่ทุกอย่าง">
การสร้าง `Worker` มีต้นทุนไม่กี่มิลลิวินาทีและ V8 isolate ของตัวเอง (ไม่มีการแชร์ memory เป็นค่าเริ่มต้น — ข้อมูลถูก copy หรือ transfer ไม่ใช่แชร์ เว้นแต่คุณจะใช้ `SharedArrayBuffer` อย่างชัดเจน) ใช้ worker เมื่องานคำนวณหนักพอ (หลักสิบมิลลิวินาทีขึ้นไป) จนความคุ้มค่าของการไม่บล็อก event loop มากกว่าต้นทุนการเริ่มต้นนั้น — ไม่ใช่สำหรับทุกการเรียกฟังก์ชัน
</Callout>

## cluster เทียบกับ reverse proxy

โมดูล `cluster` ในตัวของ Node fork process ของคุณหลายชุด (โดยทั่วไปหนึ่งชุดต่อหนึ่ง CPU core) ที่แชร์ port การฟังร่วมกัน ทำให้ใช้ multi-core ได้โดยไม่ต้องมี load balancer แยกต่างหาก:

export const clusterCode = `
import cluster from 'node:cluster';

if (cluster.isPrimary) {
  console.log('primary pid, forking 2 workers');
  cluster.fork();
  cluster.fork();
  let exited = 0;
  cluster.on('exit', () => {
    exited++;
    if (exited === 2) console.log('all workers exited, primary done');
  });
} else {
  console.log('worker running, exiting immediately');
  process.exit(0);
}
`;

export const clusterOut = `primary pid, forking 2 workers
worker running, exiting immediately
worker running, exiting immediately
all workers exited, primary done`;

<NodeRunner client:visible code={clusterCode} node expected={clusterOut} />

ในทางปฏิบัติ production ส่วนใหญ่ใช้ **reverse proxy** (nginx, cloud load balancer, หรือ container orchestrator ที่รัน N replica) แทนที่จะใช้ `cluster` โดยตรง: reverse proxy ยังจัดการ TLS termination, health check, rolling restart แบบไม่มี downtime, และ scale ในแนวนอนข้าม*เครื่อง* ไม่ใช่แค่ core บนเครื่องเดียว — `cluster` ช่วยแค่ให้ใช้ core ของเครื่องที่คุณมีอยู่แล้วเท่านั้น `cluster` ยังมีประโยชน์สำหรับ deployment เครื่องเดียว หรือเป็นกลไกที่ process manager (เช่น PM2) ใช้อยู่ข้างใน

สำหรับ load testing ทั้งสองแบบ `autocannon` (`npx autocannon http://localhost:3000`) คือเครื่องมือมาตรฐานของ Node ecosystem — มันไม่ได้มาในตัว แต่เป็นวิธีที่ใช้กันทั่วไปในการสร้าง HTTP load แบบ concurrent และดู request/sec กับ latency percentile ของ server ที่กำลังรันอยู่

## แบบจำลองความคิด (Mental Model)

ทุกเทคนิคในหน้านี้จริง ๆ แล้วตอบคำถามหนึ่งในสองข้อ: "สิ่งนี้ใช้เวลานานแค่ไหน" (`performance.now`, `mark`/`measure`, `--cpu-prof`) หรือ "มีอะไรกำลังบล็อก loop อยู่ตอนนี้หรือเปล่า ที่ไหนก็ได้ในระบบ" (`monitorEventLoopDelay`) การ optimize ไม่ใช่สิ่งที่ทำครั้งเดียวจบ — มันคือ loop นี้: วัด หา hot path จริง (ไม่ใช่ตัวที่คุณคิดเอาเอง) แก้ไขสิ่งนั้น แล้ววัดใหม่อีกครั้ง

## Trade-offs

| ตัวเลือก | ข้อดี | ต้นทุน |
|---|---|---|
| การแบ่งงานด้วย `setImmediate`/`await` | ง่าย ไม่ต้องมีเธรดใหม่ งานทั้งหมดยังอยู่บน core เดียว | CPU time รวมเท่าเดิม แค่สลับกันทำ — ไม่ได้เพิ่ม throughput |
| `worker_threads` | ขนานกันจริง main thread ยังตอบสนอง I/O ได้ | มี overhead ต่อ worker หนึ่งตัว ไม่มีการแชร์ memory เป็นค่าเริ่มต้น ต้องเขียนโค้ดประสานงานเพิ่ม |
| `cluster` (multi-process) | ใช้ทุก core บนเครื่องเดียว เปลี่ยนโค้ดน้อย | แต่ละ worker process มี memory ของตัวเอง (ไม่มี cache ที่แชร์ใน process) ยังเป็นเพดานของเครื่องเดียวอยู่ดี |
| Reverse proxy + N replica | scale ข้ามเครื่องได้ จัดการ TLS/health check/rolling restart ให้ด้วย | ต้องมี infrastructure ให้รันและดูแล แยกจากโค้ดแอปพลิเคชัน |

## ความเข้าใจผิดที่พบบ่อย

- **"การแบ่งงานด้วย setImmediate ทำให้งานเร็วขึ้น"** — ความจริง: มันทำให้ *event loop* ตอบสนองมากขึ้นด้วยการสลับงานอื่นเข้ามาคั่น CPU time รวมของงานหนักตัวนั้นไม่ได้ลดลงเลย
- **"Worker thread แชร์ memory กับ main thread โดยอัตโนมัติ"** — ความจริง: โดยค่าเริ่มต้น ข้อมูลที่ส่งเข้า/ออกจาก `Worker` ถูก structured-clone (copy) การแชร์ memory จริง ๆ ต้องใช้ `SharedArrayBuffer` และ `Atomics` อย่างชัดเจน
- **"cluster ให้ประโยชน์เหมือนกับ reverse proxy"** — ความจริง: `cluster` ใช้แค่ core บนเครื่องเดียวเท่านั้น มันไม่ได้ช่วยเรื่อง TLS termination, scale ข้ามเครื่อง, หรือ zero-downtime deploy แบบที่ reverse proxy/load balancer ทำได้
- **"performance.now() วัดสิ่งที่ทั้ง server สัมผัส"** — ความจริง: มันวัดแค่ช่วงที่คุณห่อด้วย `mark`/`measure` หรือ `t0`/`t1` เท่านั้น สิ่งอื่นทั้งหมด (dependency, GC, request อื่น) ยังอาจเป็นต้นตอ latency จริงได้ — นั่นคือสิ่งที่ `monitorEventLoopDelay` มีไว้เพื่อจับ

## อ่านโค้ดที่ AI เขียน

- โค้ดย้ายงานคำนวณไปยัง `Worker` สำหรับสิ่งที่ใช้เวลาแค่ไมโครวินาทีหรือไม่? overhead ของการสร้างเธรดและ copy ข้อมูลอาจแพงกว่าตัวงานคำนวณเอง

มีการสร้าง `PerformanceObserver` ใหม่และ `.observe()` ทุก request แต่ไม่เคย `.disconnect()` เลย แต่ละตัวยังฟัง entry `'measure'` ใหม่ต่อไปตลอดอายุที่เหลือของ process — หลังจากผ่านไปพันครั้ง observer พันตัวจะทำงาน (และ log) พร้อมกันทุกครั้งที่มีการเรียก `performance.measure()` ที่ไหนก็ตามใน process ไม่ใช่แค่ตัวที่สร้าง observer นั้นขึ้นมา นี่คือรูปแบบ listener leak: output การ log เพิ่มขึ้นเรื่อย ๆ memory สำหรับ observer ที่ค้างอยู่โตไม่มีขีดจำกัด และระบบช้าลงเรื่อย ๆ ทางแก้: สร้าง observer แค่ครั้งเดียวนอก request handler (หรือใช้ `performance.getEntriesByName()` แบบ synchronous หลัง `measure()` แทน observer เลยเมื่อไม่ต้องการเก็บข้อมูลแบบ async) และเรียก `.disconnect()` เมื่อใช้เสร็จจริง ๆ
</SpotTheBug>
