`package.json` แยก dependency ออกเป็นหลายส่วนตามจุดประสงค์การใช้งาน การเข้าใจความแตกต่างช่วยให้ production bundle มีขนาดเล็กลง ป้องกัน peer conflict และทำให้ CI builds มีความน่าเชื่อถือ

## dependencies

`dependencies` คือ package ที่โค้ดของคุณต้องการเมื่อ **ทำงานจริง** เมื่อผู้ใช้ติดตั้ง package ของคุณ npm จะ install `dependencies` เหล่านี้ไปด้วย

```json
{
  "dependencies": {
    "express": "^4.18.2",
    "zod": "^3.22.0"
  }
}
```

ติดตั้ง dependency ใหม่:

```bash
npm install express
```

## devDependencies

`devDependencies` คือ package ที่ต้องใช้เฉพาะระหว่าง **การพัฒนา** เช่น test runner, linter, bundler หรือ type definitions ไม่ถูก install เมื่อผู้ใช้ติดตั้ง package ของคุณ และไม่ถูก install ใน environment production เมื่อรัน `npm ci --omit=dev`

```json
{
  "devDependencies": {
    "vitest": "^1.2.0",
    "eslint": "^8.57.0",
    "@types/node": "^20.11.0"
  }
}
```

ติดตั้ง dev dependency:

```bash
npm install --save-dev vitest
```

## peerDependencies

`peerDependencies` ระบุ package ที่ **ผู้ใช้ต้องจัดหาเอง** วิธีนี้ป้องกันไม่ให้มี instance ซ้ำซ้อนของ library ที่ใช้ state ร่วมกัน เช่น React หรือ webpack

```json
{
  "peerDependencies": {
    "react": ">=17.0.0"
  }
}
```

npm 7 ขึ้นไปจะ install peer dependencies โดยอัตโนมัติ แต่จะแจ้งเตือนหาก version ไม่ตรงกัน

## Lockfiles

npm สร้าง `package-lock.json` เมื่อรัน `npm install` ครั้งแรก lockfile นี้ระบุ version ที่แน่นอนของทุก dependency (รวมถึง dependency ลำดับที่สอง) เพื่อให้ทุกคนในทีมและ CI ได้รับ dependency tree ที่เหมือนกันทุกประการ

```json
{
  "name": "my-app",
  "lockfileVersion": 3,
  "requires": true,
  "packages": {
    "node_modules/express": {
      "version": "4.18.2",
      "resolved": "https://registry.npmjs.org/express/-/express-4.18.2.tgz",
      "integrity": "sha512-..."
    }
  }
}
```

Lockfile entry แต่ละอันมีฟิลด์ `integrity` ด้วย — hash แบบ base64 ของ byte ของ tarball จริงที่ npm resolve มา นี่คือสิ่งที่ทำให้ `npm ci` เป็น security boundary ไม่ใช่แค่ version pin: การ re-download ที่ได้ byte ต่างออกไป (registry ที่ถูก compromise, การส่งที่เสียหาย, mirror ที่ถูกแก้ไข) จะ fail การตรวจ hash แทนที่จะติดตั้งไปอย่างเงียบๆ

export const integrityCode = `
const crypto = require('node:crypto');

function integrityOf(content) {
  return 'sha512-' + crypto.createHash('sha512').update(content).digest('base64');
}

// A lockfile entry pins the exact integrity hash npm recorded at install time.
const lockedIntegrity = integrityOf('demo-package@1.0.0 tarball bytes');

// A later "npm ci" re-downloads the tarball and re-hashes it before trusting it.
const redownloaded = integrityOf('demo-package@1.0.0 tarball bytes');
console.log('matches lockfile:', redownloaded === lockedIntegrity);

// A tampered or corrupted tarball hashes differently — npm ci fails closed.
const tampered = integrityOf('demo-package@1.0.0 tarball bytes (modified)');
console.log('tampered matches lockfile:', tampered === lockedIntegrity);
`;

export const integrityOut = `matches lockfile: true
tampered matches lockfile: false`;

## npm install เทียบกับ npm ci

```bash
# npm install — อัปเดต lockfile หากไม่ตรงกับ package.json
npm install

# npm ci — ใช้ lockfile ทุกอย่างตามตัวอักษร; ล้ม node_modules เก่าก่อนเสมอ
# จะ fail หาก package-lock.json ไม่ sync กับ package.json
npm ci
```

ใช้ `npm install` ระหว่างพัฒนาเมื่อต้องการอัปเดต dependency ใช้ `npm ci` ใน CI/CD และ Docker build เพื่อให้ได้ reproducible install ที่เร็วและปลอดภัย

<Callout title="Commit lockfile ของคุณ และใช้ npm ci ใน CI">
`package-lock.json` ควร commit เข้า version control เสมอ — ไม่ใช่แค่ `package.json` เพียงอย่างเดียว lockfile รับประกันว่า CI, Docker build และเครื่องของเพื่อนร่วมทีมทุกคนได้รับ dependency tree ที่เหมือนกันทุกประการ ใช้ `npm ci` แทน `npm install` ใน automated environment เพื่อให้ build fail อย่างชัดเจนเมื่อ lockfile ไม่ sync
</Callout>

คำกล่าวอ้าง "fail อย่างชัดเจน" ของ `npm ci` ไม่ใช่ทฤษฎี — นี่คือ transcript จริง โปรเจกต์หนึ่งติดตั้ง lockfile แล้ว `package.json` drift ออกไป (เพิ่ม dependency ด้วยมือโดยไม่ได้รัน `npm install` ใหม่):

```bash
npm ci
```

```text
npm error code EUSAGE
npm error
npm error `npm ci` can only install packages when your package.json and package-lock.json or npm-shrinkwrap.json are in sync. Please update your lock file with `npm install` before continuing.
npm error
npm error Missing: is-odd@3.0.1 from lock file
npm error Missing: is-number@6.0.0 from lock file
```

มันไม่พยายาม reconcile หรือติดตั้งบางส่วนเลย — มัน refuse ทั้งหมด นี่คือ failure mode ที่ควรจับ lockfile ที่ล้าสมัยได้ใน CI ก่อนที่ dependency tree ที่แย่จะไปถึง production

### Anti-pattern ของ Dockerfile

จุดที่ความแตกต่างนี้ถูกทำผิดบ่อยที่สุดคือ Dockerfile การใช้ `npm install` ใน image build ทำลายจุดประสงค์ทั้งหมดของ lockfile — image build แต่ละครั้งสามารถ resolve transitive version ต่างกันเล็กน้อย แม้จาก `package.json` เดียวกันเป๊ะ:

```text
# Anti-pattern: npm install in a Docker image
FROM node:24-slim
WORKDIR /app
COPY package.json package-lock.json ./
RUN npm install --omit=dev
COPY . .
CMD ["node", "server.js"]
```

```text
# Correct: npm ci pins the exact tree the lockfile recorded
FROM node:24-slim
WORKDIR /app
COPY package.json package-lock.json ./
RUN npm ci --omit=dev
COPY . .
CMD ["node", "server.js"]
```

`npm ci --omit=dev` ยังลบ `node_modules` ก่อนติดตั้งด้วย ดังนั้น layer เก่าจาก build ก่อนหน้าจึงไม่มีทาง leak package dev-only (หรือแย่กว่านั้นคือ version อื่นของ dependency จริง) เข้าไปใน production image ได้ `npm install` ใน Dockerfile คือบั๊กจริง ไม่ใช่แค่เรื่อง style: build สองครั้งจาก source tree เดียวกันเป๊ะ ห่างกันหลายวัน สามารถสร้าง image ที่ต่างกัน ไม่ reproducible ได้

## `overrides`

`overrides` บังคับ version ที่กำหนดสำหรับ dependency **ที่ไหนก็ตามที่มันปรากฏใน tree** รวมถึงที่ซ้อนอยู่ภายใน dependency ที่คุณไม่ได้ควบคุม — เครื่องมือสำหรับ transitive package ที่ถูก pin ไว้ที่ version เก่าที่มีช่องโหว่ ที่ maintainer ของมันเองยังไม่ bump

```json
{
  "overrides": {
    "minimatch": "^3.1.2"
  }
}
```

Before/after จริง capture มาจากโปรเจกต์ที่มี direct dependency ตัวเดียวที่ตัวมันเอง pin `minimatch` เก่าที่มีช่องโหว่แบบตรงเป๊ะ:

```bash
npm ls minimatch
```

```text
overrides-demo@1.0.0 /path/to/overrides-demo
└─┬ outer-lib@1.0.0 -> ./outer
  └── minimatch@3.0.4
```

```json
{
  "overrides": { "minimatch": "^3.1.2" }
}
```

```bash
npm install && npm ls minimatch
```

```text
overrides-demo@1.0.0 /path/to/overrides-demo
└─┬ outer-lib@1.0.0 -> ./outer
  └── minimatch@3.1.5
```

`minimatch` transitive ย้ายจาก `3.0.4` ไปเป็น `3.1.5` โดยไม่ต้องแตะ `outer-lib` เลย `overrides` บังคับ version ที่ขัดกับ peer requirement ของ dependency เองไม่ได้ — npm ยังตรวจ compatibility อยู่ — แต่มันคือเครื่องมือที่ถูกต้องสำหรับสถานการณ์แบบนี้เป๊ะ ที่การรอให้ maintainer ทุกคนตลอดสาย publish bump ไม่ใช่ตัวเลือก

## `npm audit`

`npm audit` ตรวจ dependency ที่ติดตั้งกับ npm security advisory database และรายงานช่องโหว่ที่รู้จัก พร้อม severity และวิธีแก้ที่แนะนำ ผลลัพธ์จริงบนโปรเจกต์ที่ pin `minimatch` เก่าไว้โดยตั้งใจ:

```bash
npm audit
```

```text
# npm audit report

minimatch  <=3.1.3
Severity: high
minimatch ReDoS vulnerability - https://github.com/advisories/GHSA-f8q6-p94x-37v3
minimatch has a ReDoS via repeated wildcards with non-matching literal in pattern - https://github.com/advisories/GHSA-3ppc-4f35-3m26
minimatch has ReDoS: matchOne() combinatorial backtracking via multiple non-adjacent GLOBSTAR segments - https://github.com/advisories/GHSA-7r86-cg39-jmmj
minimatch ReDoS: nested *() extglobs generate catastrophically backtracking regular expressions - https://github.com/advisories/GHSA-23c5-xmqv-rm74
fix available via `npm audit fix --force`
Will install minimatch@3.1.5, which is outside the stated dependency range
node_modules/minimatch

1 high severity vulnerability
```

`npm audit fix` apply fix ที่ยังอยู่ใน semver range เดิม; `npm audit fix --force` จะติดตั้ง version ที่**นอก**ช่วงที่ประกาศไว้ (ตามที่ flag ไว้ข้างบน) เพื่อปิดช่องโหว่ ซึ่งอาจเป็น breaking change — ควร review เสมอก่อนรันมันแบบไม่มีคนดูใน CI

## Workspaces

Workspaces ให้ root `package.json` ตัวเดียวจัดการหลาย package ใน repository เดียว (monorepo) โดย symlink cross-package dependency เข้าไปใน `node_modules` ของแต่ละ package แทนที่จะ publish แล้วติดตั้งใหม่ทุกครั้งที่มีการเปลี่ยนแปลง

```json
{
  "name": "my-monorepo",
  "private": true,
  "workspaces": ["packages/*"]
}
```

## Mental Model

ทุกคำสั่งจัดการ dependency ในบทนี้ตอบคำถามเดียวกัน: **"byte ที่แน่ชัดที่ฉันกำลังจะรันคืออะไร และฉันเชื่อที่มาของมันได้ไหม"** Lockfile ตอบคำถามนี้สำหรับการติดตั้งครั้งเดียว (integrity hash) `npm ci` ตอบสำหรับทั้ง environment (fail ถ้า lockfile กับ manifest ไม่ตรงกัน ล้าง `node_modules` ก่อนเสมอ) `overrides` ตอบเมื่อ transitive dependency ที่คุณไม่ได้ควบคุม ship สิ่งที่คุณต้องบังคับเปลี่ยนอยู่ดี `npm audit` ตอบเทียบกับ public vulnerability database ไม่มีอันไหนเกี่ยวกับ "ทำให้ dependency ทำงาน" — ทั้งหมดเกี่ยวกับการทำให้แน่ใจว่าสิ่งที่ติดตั้งจริงตรงกับสิ่งที่คุณเชื่อว่าติดตั้งไป

## Trade-offs

| ตัวเลือก | ประโยชน์ | ต้นทุน |
|---|---|---|
| `npm ci` ใน CI/Docker | Reproducible, เร็ว (ไม่มีขั้นตอน resolve), fail ชัดเจนเมื่อ drift | ใช้เพิ่มหรืออัปเดต dependency ไม่ได้ — ยังต้อง `npm install` ในเครื่อง local ก่อน |
| `overrides` สำหรับ transitive pin | แก้ dependency ที่มีช่องโหว่/พังที่ซ้อนอยู่โดยไม่ต้อง fork หรือรอ maintainer | ข้าม version ที่ maintainer เทสต์ไว้แล้ว — อาจสร้าง incompatibility ที่ override ไม่รู้ |
| `npm audit fix --force` | ปิดช่องโหว่ที่ fix ปกติของ npm เข้าไม่ถึง | ติดตั้ง version นอกช่วงอัตโนมัติ — เป็นการเปลี่ยน behavior จริง ไม่ใช่แค่ patch |
| Workspaces | Iterate ในเครื่องได้เร็วข้าม package, ไม่ต้อง publish-แล้วติดตั้งใหม่วนไป | เพิ่มความซับซ้อนของ tooling monorepo; บั๊กที่เกิดเฉพาะใน workspace อาจมองไม่เห็นจนกว่า package จะถูก publish แยกกันจริง |

## Common Misconceptions

- **"`npm ci` แค่เป็น `npm install` ที่เร็วกว่า"** มันเป็น contract ที่ต่างกัน: มัน refuse รันทั้งหมดถ้า `package.json` กับ lockfile ไม่ตรงกัน และมันลบ `node_modules` ก่อนเสมอ ความเร็วเป็นแค่ผลข้างเคียง ไม่ใช่จุดประสงค์
- **"`overrides` มีผลแค่กับ direct dependency ของคุณเองเท่านั้น"** มันเข้าถึงทั้ง tree รวมถึง package ที่ซ้อนอยู่หลายชั้นที่คุณไม่เคยระบุใน `package.json` ของตัวเองเลย
- **"`npm audit fix` กับ `npm audit fix --force` ทำสิ่งเดียวกัน แค่แรงกว่า"** เวอร์ชันธรรมดา apply fix เฉพาะที่อยู่ใน semver range เดิมของคุณ `--force` จะกระโดดไป version นอกช่วงที่ประกาศไว้ — เป็น upgrade จริง ที่มีโอกาส breaking change จริง
