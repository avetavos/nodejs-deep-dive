## The process object

`process` is a global object that gives your program access to the running Node.js process. It is available everywhere — no import required.

The most commonly used properties are:

| Property / Method | What it gives you |
|---|---|
| `process.argv` | Array of command-line arguments |
| `process.env` | Object of environment variables |
| `process.cwd()` | Current working directory string |
| `process.exit(code)` | Terminate the process with an exit code |
| `process.platform` | OS platform string (`'linux'`, `'darwin'`, `'win32'`) |
| `process.version` | Node.js version string (e.g. `'v20.11.0'`) |

## process.argv — command-line arguments

`process.argv` is always an array. The first two elements are fixed:

- `argv[0]` — path to the `node` binary
- `argv[1]` — path to the script being run
- `argv[2]` onwards — your actual arguments

export const argvCode = `
// Run as: node index.js hello world
// argv[0] = node binary path
// argv[1] = script path
// argv[2+] = your arguments

var args = process.argv.slice(2);
console.log('All argv:', process.argv);
console.log('User args only:', args);
console.log('Arg count:', args.length);
`;

## process.env — environment variables

`process.env` is a plain object whose keys and values are strings. It is populated from the shell environment at process startup.

export const envCode = `
// Read a variable (returns undefined if not set)
var nodeEnv = process.env.NODE_ENV;
console.log('NODE_ENV:', nodeEnv);

// Provide a default with the || operator
var port = process.env.PORT || '3000';
console.log('PORT:', port);

// All env keys
var keys = Object.keys(process.env);
console.log('Total env vars:', keys.length);
`;

<NodeRunner client:visible code={envCode} node />

### Every value is a string — the PORT > 1024 trap

Every key and value in `process.env` is a **string**, even if the shell set it to something that looks like a number or a boolean. `PORT=3000` in the environment gives you `process.env.PORT === '3000'`, not `3000`. Relational operators (`<`, `>`) coerce a string operand to a number for you, but `===` and `+` do not — that mismatch is one of the most common `process.env` bugs:

export const envStringsCode = `
process.env.PORT = '3000'; // set here only to make this demo self-contained

console.log('typeof PORT:', typeof process.env.PORT);

// Trap 1: strict equality never coerces
console.log('PORT === 3000:', process.env.PORT === 3000);       // false -- string !== number
console.log('PORT === "3000":', process.env.PORT === '3000');   // true

// Trap 2: + concatenates strings instead of adding numbers
console.log('PORT + 1:', process.env.PORT + 1);                 // "30001"
console.log('Number(PORT) + 1:', Number(process.env.PORT) + 1); // 3001 -- convert first

// Relational operators DO coerce to number...
console.log('PORT > 1024:', process.env.PORT > 1024); // true

// ...but an unset variable coerces to NaN, and every comparison with NaN
// is false -- silently, with no error, instead of telling you it's missing.
delete process.env.PORT;
console.log('unset PORT > 1024:', process.env.PORT > 1024);   // false, NOT an error
console.log('Number(unset PORT):', Number(process.env.PORT)); // NaN
`;

export const envStringsOut = `typeof PORT: string
PORT === 3000: false
PORT === "3000": true
PORT + 1: 30001
Number(PORT) + 1: 3001
PORT > 1024: true
unset PORT > 1024: false
Number(unset PORT): NaN`;

<NodeRunner client:visible code={envStringsCode} node expected={envStringsOut} />

<Callout title="Always convert before comparing or doing arithmetic">
`Number(process.env.PORT)` (or `parseInt(process.env.PORT, 10)`) before comparing with `===` or using `+`. And check the result isn't `NaN` — an unset or malformed env var fails silently otherwise, instead of crashing loudly where you'd notice it in development.
</Callout>

### Loading a .env file without dotenv

Since Node 22 the runtime loads env files itself — from the CLI with `--env-file`, or from code with `process.loadEnvFile()`:

```bash
node --env-file=.env src/app.js
```

```js
import { writeFileSync, unlinkSync } from 'node:fs';
import { loadEnvFile } from 'node:process';

writeFileSync('.env', 'PORT=4000\n'); // demo fixture
loadEnvFile();              // defaults to ./.env
console.log(process.env.PORT);
unlinkSync('.env');
```

<Callout title="Read config from process.env, not hardcoded values">
Never hardcode secrets, ports, or host names in source code. Read them from `process.env` at startup. This follows the 12-Factor App principle and lets you deploy the same code to development, staging, and production by changing only environment variables — no code changes required.
</Callout>

## process.exit()

`process.exit(code)` terminates the process immediately. By convention:
- Exit code `0` means success.
- Any non-zero code (typically `1`) means failure.

```js
// @expect-throw
// Example: exit with error if a required env var is missing
if (!process.env.DATABASE_URL) {
  console.error('ERROR: DATABASE_URL is required');
  process.exit(1);
}
```

Calling `process.exit()` is a hard stop — it skips pending async callbacks **and** any `finally` blocks still on the call stack. Prefer setting `process.exitCode` (e.g. `process.exitCode = 1`) and letting the process exit naturally instead — that gives pending I/O, `finally` blocks, and a graceful shutdown (e.g. `server.close()`) a chance to run.

export const exitCodeCode = `
process.exitCode = 1; // tentative -- overwritten below once cleanup finishes

console.log('exitCode set to 1 (tentative)');

setImmediate(function() {
  console.log('setImmediate callback ran -- exitCode does NOT skip pending callbacks');
  process.exitCode = 0; // cleanup succeeded -- exit 0 once the loop naturally drains
});
`;

export const exitCodeOut = `exitCode set to 1 (tentative)
setImmediate callback ran -- exitCode does NOT skip pending callbacks`;

<NodeRunner client:visible code={exitCodeCode} node expected={exitCodeOut} />

export const hardExitCode = `// @expect-throw
console.log('about to hard-exit with process.exit(1)');
process.exit(1);
setImmediate(function() {
  console.log('this NEVER prints -- process.exit() skips pending callbacks');
});
`;

export const hardExitOut = `about to hard-exit with process.exit(1)`;

<NodeRunner client:visible code={hardExitCode} node expected={hardExitOut} />

Same pending `setImmediate`, two different outcomes: `process.exitCode` lets it run before the process exits; `process.exit()` cuts it off mid-flight.

## Signals and graceful shutdown

Orchestrators (Docker, Kubernetes, `systemd`, `Ctrl+C` in a terminal) stop a process by sending it a signal, not by killing it outright: `SIGTERM` asks nicely, `SIGINT` is what `Ctrl+C` sends. Node lets you intercept both with `process.on()` to finish in-flight work — stop accepting new connections, let existing requests finish, close database connections — before actually exiting:

export const sigtermCode = `
// Keeps the event loop alive long enough for the signal to actually be
// delivered -- with nothing else pending, Node can exit(0) before the
// signal ever arrives. The handler clears it once it runs.
var keepAlive = setTimeout(function() {}, 5000);

process.on('SIGTERM', function() {
  clearTimeout(keepAlive);
  console.log('SIGTERM received -- closing server gracefully');
  console.log('cleanup done, exiting 0');
  process.exit(0);
});

console.log('server started (simulated)');
// In production this signal comes from the orchestrator; here we send it to
// ourselves to make the demo self-contained and deterministic.
process.kill(process.pid, 'SIGTERM');
console.log('this line runs synchronously -- the signal handler fires after it');
`;

export const sigtermOut = `server started (simulated)
this line runs synchronously -- the signal handler fires after it
SIGTERM received -- closing server gracefully
cleanup done, exiting 0`;

<NodeRunner client:visible code={sigtermCode} node expected={sigtermOut} />

<Callout title="Without a SIGTERM handler, Docker/k8s kill you after a timeout">
With no listener, `SIGTERM` terminates the process immediately — any request being handled at that moment is cut off mid-response. Kubernetes gives a pod a grace period (default 30s) between `SIGTERM` and a hard `SIGKILL`; use that window to call `server.close()` (stop accepting new connections, let in-flight ones finish) and close any database pools before calling `process.exit(0)` yourself.
</Callout>

## process.nextTick — where it fits in the event loop

`process.nextTick(fn)` queues `fn` to run **before** the event loop continues to the next phase — even before other microtasks (promise callbacks) queued earlier. It's covered in depth, with the full ordering against `Promise`, `setImmediate`, and `setTimeout`, in [Microtasks and Macrotasks](/nodejs/en/event-loop-async/microtasks-macrotasks/). The short version relevant here: `process` is where `nextTick` lives, but it is really an event-loop primitive, not a `process`-specific feature — it exists on `process` for historical reasons (it predates `queueMicrotask`).

## The node: prefix — recap

As covered in this module's [overview](/nodejs/en/core-apis/), `process` needs no import at all — it's a true global, like `Buffer`. Every module used on this page (`node:util`, `node:fs`, `node:child_process`) can be imported with or without the `node:` prefix *if* it's a legacy module; brand-new built-ins like `node:test` and `node:sqlite` only resolve with the prefix. When you see `require('util')` in older code, it is equivalent to `require('node:util')` — the prefix is a clarity convention, not a behavior change, for anything that predates it.

## CLI parsing and terminal styling: util.parseArgs and util.styleText

`node:util` ships two small utilities that remove the need for popular npm packages in simple CLI tools. `parseArgs` (stable since 20.x) replaces `yargs`/`minimist` for straightforward flag parsing:

export const parseArgsCode = `
import { parseArgs } from 'node:util';

// Normally read from process.argv.slice(2); hardcoded here to keep the demo deterministic
var fakeArgv = ['--name', 'Ada', '--verbose', '--count', '3'];

var { values } = parseArgs({
  args: fakeArgv,
  options: {
    name: { type: 'string' },
    verbose: { type: 'boolean' },
    count: { type: 'string' },
  },
});

console.log(values);
`;

`styleText` (stable since 22.x) adds ANSI color/style codes to a string — replacing `chalk`/`picocolors` for basic cases. It automatically checks whether the target stream actually supports color and **returns the plain string unchanged if not** (piped output, a log file, most CI runners):

export const styleTextCode = `
import { styleText } from 'node:util';

var msg = styleText('green', 'OK');
console.log(JSON.stringify(msg));
// When stdout is not a TTY (as in this verified output, and in CI logs),
// styleText skips the ANSI codes entirely -- the string comes back unchanged.
console.log('length with codes:', msg.length, 'vs plain length:', 'OK'.length);
`;

## Trade-offs

| Choice | Benefit | Cost |
|---|---|---|
| Reading config via `process.env` | Same code deploys to every environment (12-Factor); no rebuild for new config | Everything is a string — every numeric/boolean value needs explicit conversion and validation |
| `process.exitCode = n` | Pending I/O, timers, and `finally` blocks get to run; safer default | Requires the event loop to actually drain — a stuck handle keeps the process alive |
| `process.exit(n)` | Guarantees immediate termination, useful when something is truly stuck | Skips `finally` blocks and pending callbacks unconditionally — including ones flushing logs or closing connections |
| Handling `SIGTERM` yourself | Requests in flight get to finish; connections close cleanly | Adds shutdown-path code that's easy to get wrong (must actually call `exit()` eventually, or the orchestrator's grace period runs out and it `SIGKILL`s you anyway) |

## Common Misconceptions

- **"process.env.PORT > 1024 is unsafe because PORT is a string"** — fact: relational operators (`<`/`>`) coerce a string operand to a number automatically; the real traps are `===` (never coerces) and `+` (concatenates strings instead of adding).
- **"process.exit() and setting process.exitCode do the same thing, just different syntax"** — fact: `exitCode` lets the event loop drain naturally — pending callbacks and `finally` blocks run; `exit()` terminates immediately, skipping both.
- **"Without a signal handler, Kubernetes waits for my process to finish its current request"** — fact: with no `SIGTERM` listener, the default behavior terminates the process right away; only an explicit handler buys time to finish in-flight work, and only up to the orchestrator's grace period.
- **"styleText always adds color codes to my string"** — fact: it checks whether the destination stream supports color first, and silently returns the plain string when it doesn't (piped output, log files, most CI).

## Reading AI-generated code

- Does code compare `process.env.SOMETHING` with `===` against a number, or feed it directly into arithmetic with `+`, without an explicit `Number(...)`/`parseInt(...)` conversion first?
- Does a script call `process.exit()` right after `console.log()` or a `fs.writeFile()`/database write, when the write might still be in flight? On some platforms buffered stdout can be truncated, and any pending async write is abandoned outright.
- Does a long-running server register a `SIGTERM`/`SIGINT` handler at all? Its absence means every deploy kills in-flight requests instead of finishing them.
- Does cleanup logic live in a `finally` block that only runs on the natural exit path, while an earlier branch calls `process.exit()` directly — silently skipping that same cleanup?

<SpotTheBug code={`import http from 'node:http';

var server = http.createServer(function(req, res) {
  res.end('ok');
});

server.listen(process.env.PORT || 3000, function() {
  console.log('listening on port', process.env.PORT || 3000);
});`}>
`process.env.PORT` is a **string** (or `undefined`). `server.listen()` happens to accept a string port number, so this specific call doesn't crash — but the moment this value is used anywhere with `===`, arithmetic, or a type check (`typeof port === 'number'`, a validation schema, a health-check comparing against a numeric range), the string type causes a silent bug. The fix is to convert once, near the top: `var port = Number(process.env.PORT) || 3000;`, so every later use of `port` is a real number.
</SpotTheBug>

<Callout title="The one-line takeaway">
Every `process.env` value is a string until you convert it, `process.exitCode` lets pending work finish while `process.exit()` cuts it off, and a `SIGTERM` handler is the difference between a graceful deploy and every in-flight request getting dropped.
</Callout>
