The *AI bug catalog* named a tool for each of its 24 patterns — mostly "none — only a human." This lesson runs every tool that *is* real, for real, against real Node.js code, and quotes exactly what came back: no invented output, no imagined rule names. None of these tools ship with this repo — each was installed in a disposable scratch project (`npm install --save-dev` for the npm packages, `brew install osv-scanner` for the one that isn't one) and run there, exactly as a reviewer would set one up for a project that does not have it yet.

## Rung 1: `node --test` with coverage

The built-in test runner needs no install at all. Given `math.cjs` exporting `add` and `subtract`, and a test file that only exercises `add`:

```js

const assert = require('node:assert/strict');
const { add } = require('./math.cjs');

  assert.equal(add(2, 3), 5);
});
```

## Rung 2: `--trace-warnings`, `--unhandled-rejections=strict`, `--trace-uncaught`

`--trace-warnings` turns a bare warning into a full stack trace pointing at exactly where the problem was created. Run against the listener-leak pattern from the *AI bug catalog*:

```text
listener count: 11
(node:45399) MaxListenersExceededWarning: Possible EventEmitter memory leak detected. 11 data listeners added to [EventEmitter]. MaxListeners is 10. Use emitter.setMaxListeners() to increase limit
    at genericNodeError (node:internal/errors:985:15)
    at wrappedFn (node:internal/errors:539:14)
    at _addListener (node:events:582:17)
    at EventEmitter.addListener (node:events:600:10)
    at handleRequest (file:///.../listener-leak.mjs:10:11)
    at file:///.../listener-leak.mjs:13:30
warning name: MaxListenersExceededWarning
```

Without the flag, the warning still prints — just without the stack, leaving "where did this listener actually get added?" as a manual search through the codebase instead of a line number.

`--unhandled-rejections=strict` has been the *default* behavior since Node 15 — running it explicitly against the floating-promise pattern produces the same crash either way:

```text
save queued
Error: missing id
    at saveRecord (...)
Node.js v24.13.0
```

The flag matters for code that still runs on an ancient Node version, or for a codebase that has deliberately overridden the default back to `warn`; on a current Node 24.13 install, the crash happens regardless.

`--trace-uncaught` adds one more section, `Thrown at:`, on top of Node's default uncaught-exception output — pointing at exactly the line the error was thrown from, separate from where it was ultimately caught (or not caught) further up the stack. Against the `error`-event-with-no-listener pattern, the default output already shows `Emitted 'error' event at:`; `--trace-uncaught` adds a second `Thrown at:` block with the same location for this simple case, but the two can differ in code where an error is thrown in one place and only surfaces to the top level somewhere else entirely.

## Rung 3: `eslint-plugin-n` + `eslint-plugin-promise`, run for real

Installed in the scratch project: `eslint@9.39.5`, `eslint-plugin-n@18.3.0`, `eslint-plugin-promise@7.3.0`. The flat config, using each plugin's own exported flat preset:

```js
// @skip-verify eslint config, not a runnable program
import n from 'eslint-plugin-n';
import promise from 'eslint-plugin-promise';

export default [
  n.configs['flat/recommended-module'],
  promise.configs['flat/recommended'],
  {
    rules: {
      'no-eval': 'error',
    },
  },
];
```

Run against a target file built to combine several *AI bug catalog* patterns at once:

```js
// @expect-throw
import fs from 'node:fs';

const data = fs.readFileSync('/etc/hosts');

function fetchUser(id) {
  return new Promise(function (ok, bad) {
    ok({ id: id });
  });
}

function handleUser(id) {
  fetchUser(id).then(function (user) {
    console.log(user);
  });
}

function chained(id) {
  return fetchUser(id).then(function (user) {
    fetchUser(user.id + 1).then(function (next) {
      console.log(next);
    });
  });
}

handleUser(1);
chained(2);

eval('console.log(1)');

process.exit(1);

new Buffer(10);
```

```text

(program)              229

finish                  53
_storeHeader            45
nextTick                44

```

`(idle)` dominates — expected for a health-check handler with no CPU-bound work — and the next-hottest real frames are all inside Node's own HTTP writing path (`writev`, `writevGeneric`, `_storeHeader`, `finish`), not application code. ## Rung 6: `knip` (unused exports)

Against a two-file scratch package where `math.js` exports `add`, `subtract`, and `multiply`, but only `add` is ever imported:

```text
Unused exports (2)
subtract  function  src/math.js:5:17
multiply  function  src/math.js:9:17
```

`knip` finds this by tracing the actual import graph, not by pattern-matching text — it is the one tool on this ladder that answers a question none of the 24 catalog patterns are really about ("is this code reachable at all?") rather than "is this reachable code correct?"

## One command for the whole ladder

```bash
node --test --experimental-test-coverage && \
  NODE_OPTIONS="--trace-warnings --unhandled-rejections=strict" node --test && \
  npx eslint . && \
  npm audit --audit-level=high
```

Four rungs, one shell line, `&&`-chained so a failure at any stage stops the rest — `--cpu-prof`/`autocannon` and `knip` are left out of the one-liner deliberately, since they need a running server and a full import graph respectively, not just a source tree to lint and test.

## Mental Model

Every rung on this ladder answers a narrow, specific question — does the code do what the tests say, did anything warn, is the style consistent, are the dependencies known-vulnerable, is it fast enough, is anything unreachable — and none of them answer "is this code correct." The pattern-to-rung table's own numbers make that concrete: 21 of 24 catalog patterns have no automated rung at all.

## Trade-offs

| Choice | Benefit | Cost |
|---|---|---|
| Running the full ladder on every PR | Catches real, if narrow, classes of bugs automatically, every time | Six separate tools, several requiring network/CI setup (`osv-scanner`, `autocannon` needing a live server) |
| Running only `node --test` + eslint | Fast enough for a pre-commit hook | Misses dependency vulnerabilities, unreachable code, and performance regressions entirely |
| Treating a clean ladder run as "reviewed" | None — this is never a good trade | Every tool here is narrow by design; a clean run only proves the narrow things it checks were fine |

## Common Misconceptions

- **"`--experimental-test-coverage` being experimental means it is unreliable."** The flag name signals the report format may still change, not that the coverage numbers it prints today are wrong — they came from real V8 coverage instrumentation, the same primitive Istanbul-based tools build on.
- **"`npm audit` and `osv-scanner` are redundant since they found the same advisories here."** They read different databases (npm's own advisory feed vs. the OSV aggregator) and can diverge on non-npm ecosystems or very recent advisories — running one is not a substitute for the other for every project.
- **"A load test with autocannon proves the server has no bugs."** It proves this *specific* handler holds up under *this* concurrency and *this* payload shape on *this* machine — it says nothing about a different route, a larger body, or a genuinely CPU-bound handler.

## Reading AI-generated code

Before trusting an AI assistant's claim that "the tests pass" or "lint is clean," reproduce it: the *AI bug catalog*'s pattern 22 exists precisely because a green `node --test` run can mean "no reachable assertion failed," not "the code is correct." Run the actual ladder above against the actual diff, read the actual rule names in the output, and check each hit against the pattern-to-rung table before deciding a tool has "handled" a concern the table says it does not cover.

<SpotTheBug code={`// PR description: "Added tests, lint is clean, ran npm audit -- all green."
function calculateDiscount(price, percent) {
  return price - percent; // BUG: should be price - (price * percent / 100)
}

import { test } from 'node:test';
test('applies a discount', function () {
  calculateDiscount(100, 10); // BUG: result never checked with an assertion
});`}>
"Lint is clean" and "npm audit is green" are both true and both irrelevant here: no eslint rule in this course's ladder checks arithmetic, and `npm audit` only scans dependencies, not this file's own logic. The only rung that could have caught the actual bug — `node --test` — reports a pass too, because the test never asserts anything about the return value. All three tools genuinely ran, and all three genuinely say nothing about whether `calculateDiscount` is correct; only reading the function body against its name catches that `100 - 10` is being returned instead of `100 - (100 * 10 / 100)`.
