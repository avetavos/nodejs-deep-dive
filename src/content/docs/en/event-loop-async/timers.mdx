## setTimeout

`setTimeout(fn, delay)` schedules `fn` to run as a **macrotask** after at least `delay` milliseconds. The delay is a **minimum** — not a guarantee. If the call stack is busy when the timer fires, the callback waits until the stack is clear.

Node clamps any delay below 1 ms up to **1 ms** — a delay of `0` or a negative number both end up firing after about 1 ms (a negative delay also logs a `TimeoutNegativeWarning`). The commonly cited "4 ms minimum" figure is a **browser** rule for timers nested 5+ levels deep — it does not apply to Node's `setTimeout`.

```js
var id = setTimeout(function() {
  console.log('Runs after at least 100 ms');
}, 100);

// Cancel before it fires:
clearTimeout(id);
```

## setInterval

`setInterval(fn, delay)` repeatedly schedules `fn` every `delay` ms. Use `clearInterval` to stop it.

```js
var count = 0;
var id = setInterval(function() {
  count++;
  console.log('tick', count);
  if (count >= 3) clearInterval(id);
}, 500);
```

## setTimeout with delay 0

`setTimeout(fn, 0)` does **not** mean "run immediately." It queues `fn` as a macrotask. Any pending microtasks (Promise callbacks, `queueMicrotask`) will run first.

```js
setTimeout(function() { console.log('Timer'); }, 0);
Promise.resolve().then(function() { console.log('Promise'); });
// Output: Promise, then Timer
```

## queueMicrotask

To schedule a callback before the next macrotask, use `queueMicrotask`:

```js
queueMicrotask(function() {
  console.log('This runs in the microtask queue, before any timer');
});
```

`setTimeout(fn, 100)` means the callback runs no sooner than 100 ms, but if the call stack is busy or other microtasks are running, it may run later. Never rely on exact timer precision for correctness.

## Promise-based timers: timers/promises and AbortSignal.timeout

`node:timers/promises` gives you a Promise-returning `setTimeout` — no callback, so it composes naturally with `await`, `Promise.race`, and an `AbortSignal`. Passing `{ signal }` lets you cancel the wait early instead of letting it run to completion:

export const timersPromisesCode = `import { setTimeout as delay } from 'node:timers/promises';

console.log('waiting 30ms with timers/promises...');
await delay(30);
console.log('done waiting');

try {
  await delay(1000, undefined, { signal: AbortSignal.timeout(20) });
  console.log('this never prints');
} catch (err) {
  console.log('aborted:', err.name);
}
`;

export const timersPromisesOut = `waiting 30ms with timers/promises...
done waiting
aborted: AbortError`;

<NodeRunner client:visible code={timersPromisesCode} node expected={timersPromisesOut} />

`AbortSignal.timeout(ms)` returns a signal that aborts itself after `ms` — a compact way to say "give up after this long" without wiring your own `setTimeout` + `AbortController` pair by hand. It works anywhere a signal is accepted: `timers/promises`, `fetch`, and any of your own code that checks `signal.aborted` or listens for `'abort'`.

## Mental Model

Every timer API is a promise about a *minimum* wait, never an exact one: `setTimeout`/`setInterval` hand a callback to libuv's timer phase, which only runs once the call stack is empty and every microtask has drained — the delay you pass is a floor, not a schedule. `timers/promises`' `setTimeout` is the same underlying timer with a Promise wrapped around it instead of a callback, which is precisely why it can be cancelled with a signal (a callback has no way to say "never mind," but a Promise can reject) — `AbortSignal.timeout(ms)` is just a pre-built signal that fires its own abort after `ms`, so you do not have to construct an `AbortController` and its own `setTimeout` by hand every time you need a deadline.

## Trade-offs

The callback-based timers (`setTimeout`, `setInterval`) have no built-in way to say "give up waiting" — you track the ID yourself and call `clearTimeout`/`clearInterval`, and there is no equivalent for "stop waiting for this to resolve" once a callback has fired. The Promise-based `timers/promises` API costs one extra import and a signal object, but buys real cancellation and composes directly with `Promise.race`/`Promise.all` — worth it for anything with a real deadline (an upstream call, a job that must not run forever) and unnecessary overhead for a plain "run this later" callback that never needs to change its mind.

## Common Misconceptions

- **"setTimeout(fn, 0) runs before anything else queued."** It runs before the *next macrotask*, but strictly after every pending microtask (`process.nextTick`, Promise reactions, `queueMicrotask`) — see the demo above, where the Promise always logs first.
- **"setTimeout(fn, 0) is basically the same as process.nextTick(fn)."** They are in different queues entirely: `nextTick` (and microtasks) drain completely after every single callback; `setTimeout(fn, 0)` waits for the next full pass through the timers phase, which can be many callbacks later under load.
- **"A 0 or negative delay means the callback runs synchronously."** It never does — even `setTimeout(fn, -100)` is clamped to Node's ~1 ms floor and still yields to the event loop first; nothing scheduled with `setTimeout` ever runs on the current stack frame.

## Reading AI-generated code

AI-generated code sometimes uses `setTimeout(fn, 0)` as an informal substitute for "the next tick" or "right after this async operation finishes" — treating it as a synchronization primitive it was never designed to be.

<SpotTheBug code={`function loadUserThenGreet(fetchUser) {
  let user = null;
  fetchUser().then(function (u) { user = u; });

  setTimeout(function () {
    // AI comment: "setTimeout(fn, 0) runs on the next tick, right after the fetch above"
    console.log('Hello, ' + user.name);
  }, 0);
}
`}>
`setTimeout(fn, 0)` is a **macrotask** with roughly a 1 ms floor — it has no relationship to how long `fetchUser()` actually takes. If `fetchUser()` does real I/O (a network call, a database query), `user` is almost certainly still `null` when the timeout fires, and `user.name` throws a `TypeError`. Even calling this "the next tick" is a misnomer: `process.nextTick` and Promise microtasks are a separate, earlier-draining queue that has nothing to do with `setTimeout`'s macrotask queue. The fix is to react to the actual Promise instead of guessing a delay: `fetchUser().then(function (u) { console.log('Hello, ' + u.name); })`.
</SpotTheBug>

<Callout title="The one-line takeaway">
A timer's delay is a floor, not a promise about relative timing to anything else in your program — never use setTimeout(fn, 0) as a stand-in for "after this Promise resolves"; await or .then() the actual Promise instead.
</Callout>
