## JavaScript is the language of Node.js

Node.js is a runtime that executes JavaScript outside the browser. Everything you write in Node — from a simple HTTP server to a complex CLI tool — is JavaScript. That means a solid grip on the language itself is non-negotiable before diving into Node's APIs.

This module covers the JavaScript fundamentals that trip up developers most in the Node ecosystem:

| Lesson | Topic |
|--------|-------|
| Types and Coercion | Primitives vs objects, `typeof`, `==` vs `===`, truthy/falsy |
| Scope and Closures | `var`/`let`/`const`, block scope, hoisting, lexical scope |
| `this` and Context | Dynamic `this`, `call`/`apply`/`bind`, arrow functions |
| Modules | ESM `import`/`export` vs CommonJS `require`, when to use each |

Modern JavaScript means **ES2022 and later** throughout — `const`/`let`, arrow functions, destructuring, `async`/`await`, optional chaining, and native ES modules. This module targets Node 24 (the active LTS); everything also runs on Node 26.

## A first runnable demo

The snippet below demonstrates several JS concepts at once: a `const` declaration, a function, a template-string-free concatenation, and a closure over the outer variable. Run it and inspect the output.

```js
const greet = function(name) {
  return 'Hello, ' + name + '!';
};

const languages = ['JavaScript', 'TypeScript', 'Node.js'];

for (const lang of languages) {
  console.log(greet(lang));
}
```

## Newer language features you will meet

Node upgrades V8 with every major release, so the language keeps growing:

- **Node 24** — `using` / `await using` for automatic resource cleanup, `RegExp.escape()`, `Error.isError()`, `Float16Array`.
- **Node 26** — the **Temporal** date/time API is enabled by default, plus `Map.prototype.getOrInsert()` and `Iterator.concat()`.

```js
  using conn = openConnection();   // the object has a [Symbol.dispose]() method
  conn.query('SELECT 1');
}                                   // conn[Symbol.dispose]() runs here, even on throw
```

## Script mode: sloppy vs strict

Every piece of JavaScript runs in one of two modes, decided by *how the file is loaded*, not by what it does:

- **Sloppy mode** — the historical default. A classic `<script>` tag in a browser, or a `.js` file in a package without `"type": "module"`, runs sloppy unless it opts out. Sloppy mode forgives mistakes that would otherwise be bugs: assigning to a name that was never declared silently creates a global variable instead of throwing, and a plain function call sets `this` to the global object instead of `undefined`.
- **Strict mode** — turns those silent forgivenesses into thrown errors. You get strict mode in three ways: writing `'use strict';` as the very first statement in a script or function, loading the file as an **ES module** (`.mjs`, or `.js` with `"type": "module"` — always strict, no directive needed), or writing code **inside a `class` body** (class bodies are strict even in an otherwise sloppy file).

## Mental Model

Think of sloppy mode as JavaScript running with a permissive safety net: typos and missing declarations get quietly absorbed instead of stopping the program. Strict mode removes that net. It does not add new features — it removes silent failure paths, converting them into thrown errors at the exact line where the mistake happened. Because ES modules and classes are strict unconditionally, and essentially all new Node.js code is written as ES modules, you should default to *assuming* strict mode and treat sloppy mode as the legacy exception you occasionally still meet in old CommonJS files.

## Trade-offs

| Mode | Benefit | Cost |
|---|---|---|
| Sloppy (legacy default) | Old scripts keep running unmodified; nothing new to learn | Typos become invisible global variables instead of errors; `this` in a plain call silently becomes the global object |
| Strict (ESM, classes, `'use strict'`) | Mistakes surface immediately as `ReferenceError`/`TypeError` at the point of the bug | A handful of legacy patterns (some `arguments` tricks, `with`) stop working — rarely missed in modern code |

## Common Misconceptions

- **"`'use strict'` is an old ES5 relic nobody needs anymore."** You still need it in plain CommonJS `.js`/`.cjs` files if you want strict guarantees there — but you get it for free, with no directive, in every ES module and every class.
- **"Strict mode changes what the code computes."** It does not add or change arithmetic or object semantics; it only turns previously-silent mistakes into thrown errors.
- **"If my file has `"type": "module"` in `package.json`, I still need `'use strict'` at the top."** No — the directive is redundant there; ESM is strict unconditionally.

## Reading AI-generated code

AI-generated snippets are frequently written and tested as quick CommonJS scripts (sloppy by default) and then assumed to behave identically once dropped into a class or an ES module. Watch for code that relies on an assignment "just working" without a preceding `const`/`let`/`var` — that is a latent bug that only a strict context (ESM, a class, or an explicit directive) will actually catch for you.

<SpotTheBug code={`function cache(key, value) {
  if (!store) store = {}; // no declaration — meant to be a shared cache
  store[key] = value;
  return store;
}

cache('a', 1);
cache('b', 2);
console.log(store); // "works" by accident today`}>
`store` is never declared with `const`/`let`/`var`. In a sloppy CommonJS script this silently creates a global named `store` the first time `cache` runs, which is why it "works" — every call happens to share the same accidental global. Drop this same function into an ES module, a class method, or add `'use strict'` to the file, and the first call throws `ReferenceError: store is not defined` instead. The fix is to declare the variable in an enclosing scope (module-level `const store = {};`) so the behavior does not depend on which mode the file happens to run in.
</SpotTheBug>
