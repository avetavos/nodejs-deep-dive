## The problem backpressure solves

Imagine a fire hose attached to a garden sprinkler. If water arrives faster than the sprinkler can spray it, the hose eventually bursts. The same thing happens in Node streams: if a fast Readable source produces data faster than a slow Writable can consume it, buffered chunks pile up in memory until the process runs out of RAM or crashes.

**Backpressure** is the mechanism by which a slow consumer tells a fast producer to slow down. It is the stream equivalent of flow control in TCP.

## How backpressure works in Node

The Writable stream's `write()` method is the key signal:

- Returns `true` — the internal buffer is below the **high-water mark** (default on Node 24: 65536 bytes (64 KiB) for byte-mode streams — both Readable and Writable — or 16 objects for object-mode streams; `fs.createReadStream` uses this same default, there is no separate exception). The producer can keep sending.
- Returns `false` — the buffer is at or above the high-water mark. The producer must **pause** and wait for the `drain` event before writing more.

The high-water mark is not a hard limit; it is a soft advisory. Node buffers chunks beyond it, but doing so costs memory. Respecting the signal keeps memory usage flat.

## Manual backpressure

Before `pipe` and `pipeline`, you had to handle this yourself:

```js
function pumpWithBackpressure(readable, writable) {
  readable.on('data', function(chunk) {
    var ok = writable.write(chunk);
    if (!ok) {
      readable.pause();             // stop the source
      writable.once('drain', function() {
        readable.resume();          // resume when ready
      });
    }
  });

  readable.on('end', function() {
    writable.end();
  });
}
```

This pattern is verbose and error-prone. One forgotten `readable.pause()` call causes the buffer to grow without bound.

## How pipe and pipeline handle it automatically

`readable.pipe(writable)` and `stream.pipeline()` implement the above pattern internally. They:

1. Forward each chunk from the readable to the writable.
2. Pause the readable when `write()` returns `false`.
3. Resume the readable on the `drain` event.

You never need to manage pausing and resuming manually when using `pipe` or `pipeline`. This is one of the primary reasons to prefer them over raw event listeners.

## Measuring what ignoring backpressure actually costs

Talking about "unbounded memory growth" is abstract. This demo makes it concrete: the same 2,000-chunk source is drained twice into the same slow sink — once through a `data` listener that ignores `write()`'s return value, and once through `.pipe()`, which respects it. Both runs track the *peak* number of chunks buffered in the sink at once:

export const unpausedCode = `
import { Readable, Writable } from 'node:stream';

function makeSource() {
  var i = 0;
  return new Readable({
    objectMode: true,
    read() {
      if (i < 2000) { this.push('chunk' + i); i++; }
      else this.push(null);
    }
  });
}

function makeSlowSink() {
  return new Writable({
    objectMode: true,
    highWaterMark: 1,
    write(chunk, enc, cb) { setImmediate(cb); } // slow relative to the fast source above
  });
}

// --- Wrong: 'data' handler ignores write()'s return value, never pauses ---
await new Promise(function(resolve) {
  var source = makeSource();
  var sink = makeSlowSink();
  var maxBuffered = 0;
  source.on('data', function(chunk) {
    sink.write(chunk); // return value ignored -- source is never paused
    if (sink.writableLength > maxBuffered) maxBuffered = sink.writableLength;
  });
  source.on('end', function() {
    console.log('ignoring backpressure -- peak buffered chunks:', maxBuffered);
    resolve();
  });
});

// --- Right: pipe() respects write()'s return value automatically ---
await new Promise(function(resolve) {
  var source = makeSource();
  var sink = makeSlowSink();
  var maxBuffered = 0;
  var timer = setInterval(function() {
    if (sink.writableLength > maxBuffered) maxBuffered = sink.writableLength;
  }, 0);
  source.pipe(sink);
  sink.on('finish', function() {
    clearInterval(timer);
    console.log('using pipe() -- peak buffered chunks:', maxBuffered);
    resolve();
  });
});
`;

export const unpausedOut = `ignoring backpressure -- peak buffered chunks: 2000
using pipe() -- peak buffered chunks: 1`;

<NodeRunner client:visible code={unpausedCode} node expected={unpausedOut} />

Ignoring the source entirely (never calling `.pause()`) lets every one of the 2,000 chunks queue up in the sink at once — the source never gets the signal to slow down. `.pipe()` keeps the sink's buffer at its high-water mark of 1 the entire time, because it pauses the source the instant `write()` returns `false`.

## Visualising backpressure with custom high-water marks

The demo below creates a Readable and a Writable with a very small high-water mark (1 byte) to make backpressure trigger on every chunk. Watch how the readable is automatically paused and resumed.

export const backpressureCode = `
const { Readable, Writable, pipeline } = require('node:stream');

const source = Readable.from(['a', 'b', 'c', 'd', 'e'], {
  objectMode: true,
  highWaterMark: 1
});

const sink = new Writable({
  objectMode: true,
  highWaterMark: 1,
  write(chunk, encoding, callback) {
    console.log('sink writing: ' + chunk);
    // simulate a slow sink
    setTimeout(callback, 10);
  }
});

pipeline(source, sink, function(err) {
  if (err) {
    console.error('error:', err.message);
  } else {
    console.log('done — pipeline handled backpressure automatically');
  }
});
`;

export const backpressureOut = `sink writing: a
sink writing: b
sink writing: c
sink writing: d
sink writing: e
done — pipeline handled backpressure automatically`;

## Trade-offs

| Choice | Benefit | Cost |
|---|---|---|
| Ignoring `write()`'s return value | Simplest possible code | Unbounded memory growth the moment the source outpaces the sink — an eventual OOM crash under real load |
| Manual pause/resume on `drain` | Full control over exactly when to slow down | Verbose, and every additional stream in a chain multiplies the chances of missing a case |
| `.pipe()` / `pipeline()` | Backpressure handled correctly with zero manual bookkeeping | Less visibility into exactly when pausing happens — you trust the implementation |

## Common Misconceptions

- **"A `data` listener is safe as long as I don't `console.log` too much"** — fact: the danger isn't logging, it's writing chunks to a *slower* destination (a socket, a file, another API) without checking whether it can keep up — that's what actually accumulates in memory.
- **"Backpressure is a Node-specific concept"** — fact: it's the general problem of a fast producer overwhelming a slow consumer — the same idea as TCP flow control, and Node streams solve it the same way (a signal to pause, and a signal to resume).
- **"A small high-water mark means small memory usage overall"** — fact: it bounds how much *one* stream buffers, but if you ignore its `write()` signal entirely (as the demo above shows), the high-water mark is irrelevant — the caller keeps writing regardless.

## Reading AI-generated code

- Does a `data` listener write to (or otherwise hand off to) something that could be slow — a socket, another stream, an external API call — without ever checking that destination's own backpressure signal?
- Does code implement a custom pump between two streams (rather than using `.pipe()`/`pipeline()`) without a `drain` listener anywhere?
- Is there a comment claiming "handles backpressure" next to code that never calls `.pause()`, checks `write()`'s return value, or delegates to `.pipe()`/`pipeline()`?

<SpotTheBug code={`const { Readable } = require('node:stream');
const net = require('node:net');

function forwardToSocket(readable, socket) {
  readable.on('data', function(chunk) {
    socket.write(chunk); // return value never checked, readable never paused
  });
}`}>
`forwardToSocket` never checks `socket.write(chunk)`'s return value and never calls `readable.pause()`. If the network socket is slower than the readable's data rate (a common situation over a real network, versus a fast in-process source), Node keeps buffering unsent chunks in the socket's internal write buffer without limit, and memory grows until the process runs out or the connection is dropped. The fix is either the manual pause/drain pattern from earlier in this lesson, or simply `readable.pipe(socket)`, which applies that exact pattern automatically.
</SpotTheBug>

<Callout title="The one-line takeaway">
Backpressure is `write()`'s boolean return value telling you to slow down — ignoring it (a raw `data` listener that never checks it) is the single most common way a Node process quietly grows without bound until it crashes.
</Callout>
