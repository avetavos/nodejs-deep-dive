Publishing a package makes it available on the npm registry so that anyone (or members of your organisation) can install it with `npm install`. The process involves three steps: preparing `package.json` with the right metadata, bumping the version, and running `npm publish`. Each step has guardrails that help you ship clean, predictable releases.

## Key `package.json` fields for publishing

A package ready to publish typically carries these fields, on top of `name` and `version`:

```json
{
  "name": "@myorg/my-util-lib",
  "version": "1.0.0",
  "description": "A small utility library",
  "license": "MIT",
  "main": "./dist/index.cjs",
  "module": "./dist/index.mjs",
  "types": "./dist/index.d.ts",
  "files": ["dist", "README.md"],
  "bin": {
    "my-util": "./dist/cli.js"
  },
  "exports": {
    ".": {
      "types": "./dist/index.d.ts",
      "import": "./dist/index.mjs",
      "require": "./dist/index.cjs",
      "default": "./dist/index.cjs"
    },
    "./helpers": {
      "types": "./dist/helpers.d.ts",
      "import": "./dist/helpers.mjs",
      "require": "./dist/helpers.cjs"
    }
  },
  "engines": {
    "node": ">=18.0.0"
  }
}
```

- **`license`** — the SPDX identifier consumers and registry scanners check before depending on your package.
- **`main`** / **`module`** — legacy CJS entry point, and a bundler-only convention some older tools still look for; both are superseded by `exports` but keep tooling compatible.
- **`types`** — the root TypeScript declaration file, used by editors and `tsc` when the package has no `exports` map or as a fallback.
- **`files`** — an allowlist of paths included in the published tarball. Everything else (source files, test fixtures, config) is excluded. If omitted, npm still applies a default set of exclusions (`node_modules`, `.git`, anything matched by `.npmignore` or, absent that, `.gitignore`).
- **`bin`** — maps a CLI command name to an entry-point script. npm creates a symlink in `.bin/` so the command is available in the PATH when the package is installed, and via `npx`.
- **`exports`** — declares the public API surface. Any path not listed here is inaccessible to consumers. Inside each conditions object, `"types"` must come first — see [Module Resolution](/nodejs/en/modules-npm/resolution/#exports-condition-order-is-significant) for why key order matters.

## The `files` field

```json
{
  "files": ["dist", "README.md", "LICENSE"]
}
```

`"files"` is an allowlist, not a denylist: only the paths listed here (plus a few files npm always includes, like `package.json` and `README`) end up in the tarball. This keeps source maps, test fixtures, and local config out of what consumers download.

The demo below reimplements that allowlist logic directly with `fs`, against a fake package tree that includes a `.env` file and test/source folders never listed in `"files"`, to make the filtering mechanism concrete rather than asserted:

export const filesFilterCode = `
const fs = require('node:fs');
const path = require('node:path');

const root = path.join(__dirname, 'fake-pkg');
fs.mkdirSync(path.join(root, 'dist', 'nested'), { recursive: true });
fs.mkdirSync(path.join(root, 'src'), { recursive: true });
fs.mkdirSync(path.join(root, 'test'), { recursive: true });
fs.writeFileSync(path.join(root, 'package.json'), JSON.stringify({
  name: 'my-util-lib', version: '1.0.0', files: ['dist', 'README.md'],
}, null, 2));
fs.writeFileSync(path.join(root, 'README.md'), '# my-util-lib\\n');
fs.writeFileSync(path.join(root, '.env'), 'SECRET=1\\n');
fs.writeFileSync(path.join(root, 'dist', 'index.js'), 'module.exports = {};\\n');
fs.writeFileSync(path.join(root, 'dist', 'nested', 'helper.js'), 'module.exports = {};\\n');
fs.writeFileSync(path.join(root, 'src', 'index.ts'), 'export {};\\n');
fs.writeFileSync(path.join(root, 'test', 'index.test.js'), '// test\\n');

// npm always includes package.json and a README regardless of "files";
// everything else must be listed in "files" (or its subdirectories) to ship.
const ALWAYS_INCLUDED = new Set(['package.json', 'README.md']);

function walk(dir, base) {
  const out = [];
  for (const entry of fs.readdirSync(dir, { withFileTypes: true })) {
    const full = path.join(dir, entry.name);
    if (entry.isDirectory()) out.push(...walk(full, base));
    else out.push(path.relative(base, full));
  }
  return out;
}

const pkg = JSON.parse(fs.readFileSync(path.join(root, 'package.json'), 'utf8'));
const allFiles = walk(root, root);
const included = allFiles.filter((rel) => {
  if (ALWAYS_INCLUDED.has(rel)) return true;
  return pkg.files.some((allowed) => rel === allowed || rel.startsWith(allowed + path.sep));
});

console.log('Would ship in the tarball:');
for (const f of included.sort()) console.log(' ', f.split(path.sep).join('/'));
console.log('Excluded (not in "files"):');
for (const f of allFiles.filter((f) => !included.includes(f)).sort()) console.log(' ', f.split(path.sep).join('/'));

fs.rmSync(root, { recursive: true, force: true });
`;

  dist/index.js

  package.json
Excluded (not in "files"):
  .env
  src/index.ts
  test/index.test.js`;

## The `bin` field

```json
{
  "bin": {
    "my-util": "./dist/cli.js"
  }
}
```

When the package is installed (locally or globally), npm creates a `my-util` executable in `node_modules/.bin/` (or the global bin directory) pointing at `./dist/cli.js`. That is what makes the command available to `npx my-util` and to `npm run` scripts in a consuming project without a global install.

## `npx` vs `npm exec` vs `node --run`

All three end up running "some code," which is exactly why generated snippets swap between them without noticing they are not equivalent:

| Command | Runs | Falls back to installing from the registry? | Runs `pre`/`post` lifecycle scripts? |
|---|---|---|---|
| `npx <bin-name>` | A `bin` entry — local (`node_modules/.bin`) if present, otherwise a temporary registry install | Yes (prompts unless `--yes`/`-y`) | N/A — not a `package.json` script |
| `npm exec -- <bin-name>` | The same `bin` lookup as `npx` (npm 7+ implements `npx` on top of `exec`) | Yes, same behavior as `npx` | N/A — not a `package.json` script |
| `node --run <script-name>` | A named script in `package.json`'s `"scripts"` field, directly — no shell spawned | No — it only runs what's already in `"scripts"` | **No** — this is the sharpest difference from `npm run` |

Real transcripts, all local and offline (a `bin` entry `say-hi` and a script `greet` both defined in the same package):

```bash
npx say-hi
```

```text
hi from local bin
```

```bash
npm exec -- say-hi
```

```text
hi from local bin
```

```bash
node --run greet
```

```text
hi from local bin
```

All three print the same thing here — but add a `pregreet` lifecycle script and the difference becomes visible:

```bash
npm run greet
```

```text
> run-demo@1.0.0 pregreet
> echo PRE-HOOK-RAN

PRE-HOOK-RAN

> run-demo@1.0.0 greet
> node cli.js

hi from local bin
```

```bash
node --run greet
```

```text
hi from local bin
```

`node --run` skips `pregreet` entirely — it executes only the named script, with no lifecycle hook resolution and no shell in between, which is also why it starts faster than `npm run`. It is a substitute for `npm run <script>`, not for `npx`/`npm exec`: it cannot install anything, and it cannot run an arbitrary binary that isn't already a `package.json` script.

## Versioning with Semantic Versioning

npm follows **semantic versioning** (semver): `MAJOR.MINOR.PATCH`.

- **PATCH** — backwards-compatible bug fixes.
- **MINOR** — backwards-compatible new features.
- **MAJOR** — breaking changes.

Use `npm version` to bump and tag in one step:

```bash
# Patch bump: 1.0.0 → 1.0.1 (bug fixes)
npm version patch

# Minor bump: 1.0.1 → 1.1.0 (backwards-compatible new features)
npm version minor

# Major bump: 1.1.0 → 2.0.0 (breaking changes)
npm version major
```

Each command updates the `"version"` field in `package.json`, commits the change, and creates a signed git tag (e.g. `v1.0.1`). Push the tag with `git push --follow-tags`.

## Testing before publish with `npm pack`

`npm pack` bundles your package into a `.tgz` tarball exactly as npm would if you ran `npm publish` — but it stays local. This lets you inspect the final artifact before shipping it. `--dry-run` goes one step further: it lists the tarball contents without writing anything to disk, and needs no registry login.

```bash
# Create a local tarball (e.g. myorg-my-util-lib-1.0.0.tgz)
npm pack

# Inspect its contents without extracting
tar -tzf myorg-my-util-lib-1.0.0.tgz

# Install it locally in another project to smoke-test
npm install ../my-util-lib/myorg-my-util-lib-1.0.0.tgz
```

Real output of `npm pack --dry-run` against a package with `"files": ["dist", "README.md"]`, a `.env`, and an unrelated secrets file sitting alongside them:

## Publishing with `npm publish`

You must be authenticated (`npm login`) before publishing. npm reads `package.json` to determine the registry target (defaults to `https://registry.npmjs.org`).

```bash
# Log in to the registry
npm login

# Publish a public (unscoped) package
npm publish

# Publish a scoped package as public (scoped packages default to restricted)
npm publish --access public

# Publish under a dist-tag other than "latest" (e.g. a beta)
npm publish --tag beta
```

## Provenance, 2FA, and the pre-publish checklist

A published version cannot be unpublished after 72 hours (npm's abuse-prevention window), so the guardrails belong **before** `npm publish` runs, not after:

- **`prepublishOnly`** — a `package.json` script npm runs automatically right before packing, and *only* before a real `npm publish` (unlike `prepublish`, which historically also ran on plain `npm install`). Put your build and test steps here so a broken build cannot ship:
  ```json
  {
    "scripts": {
      "prepublishOnly": "npm test && npm run build"
    }
  }
  ```
- **`npm pack --dry-run`** — the free, local, no-login-required check from the previous section. Run it and actually read the file list before every publish.
- **Two-factor authentication (2FA)** — `npm profile enable-2fa auth-and-writes` requires a one-time code (or a hardware security key) for both login and publish, so a leaked npm token alone is not enough to publish a malicious version under your name.
- **Provenance (`npm publish --provenance`)** — from a supported CI environment (GitHub Actions, GitLab CI), this cryptographically attaches the exact source commit and build workflow that produced the tarball, publicly visible on the npm registry page. It answers "was this actually built from the public source repo" for anyone auditing a supply-chain incident.

## Scoped packages

A **scoped package** uses the `@scope/name` format and is typically used for organisation namespacing or to group related packages:

```json
{
  "name": "@myorg/my-util-lib",
  "version": "1.0.0"
}
```

Scoped packages are **private by default** on the npm registry. To publish them publicly, always pass `--access public`:

```bash
# Scaffold a scoped package
npm init --scope=@myorg

# Publish it publicly
npm publish --access public
```

Private scoped packages require a paid npm account or a private registry.

## Mental Model

Everything in this lesson exists because **`npm publish` is closer to a one-way door than a save button**. A published tarball's exact bytes are permanent — you cannot edit or silently replace `1.0.0` after the fact — so every guardrail here (`"files"`, `prepublishOnly`, `npm pack --dry-run`, 2FA, provenance) exists to catch a mistake in the few seconds *before* that door closes, because nothing catches it after.

## Trade-offs

| Choice | Benefit | Cost |
|---|---|---|
| `prepublishOnly` running tests/build | A broken build cannot be published — the check runs automatically, no one has to remember it | Adds real time to every publish; a flaky test can block a legitimate release |
| 2FA on publish | A stolen npm token alone cannot publish a malicious version | Every publish needs a second factor available — friction for automated release pipelines unless a granular token is set up |
| `--provenance` | Public, verifiable link between a published tarball and the exact source commit/workflow that built it | Only works from a supported CI provider — cannot be added retroactively to already-published versions |
| Strict `"files"` allowlist | Small, predictable tarballs; nothing accidentally shipped | Forgetting to add a genuinely needed file (a wasm binary, a font) breaks the package for consumers until the next version |

## Common Misconceptions

- **"I can just publish a patch to fix a mistake I shipped."** You can publish a *new* version, but the broken one stays on the registry forever (npm's unpublish window is 72 hours and has restrictions even within it) — anyone who already resolved that exact version keeps the mistake.
- **"`npm pack` and `npm publish` might package different files."** They use the identical `"files"`/`.npmignore` logic — `npm pack --dry-run` is not an approximation, it is the literal tarball-building step, minus the upload.
- **"2FA only protects my npm account login."** `enable-2fa auth-and-writes` additionally requires a second factor for the publish itself — a stolen or leaked auth token is not sufficient on its own to push a malicious version.

## Reading AI-generated code

Generated CI/CD publish scripts frequently omit `prepublishOnly` and go straight from a version bump to `npm publish`, because the tutorial-shaped examples most training data comes from are demonstrating "how to publish," not "how to publish safely."

<SpotTheBug code={`{
  "name": "my-cli-tool",
  "version": "1.0.0",
  "bin": { "my-cli": "./dist/cli.js" },
  "devDependencies": {
    "commander": "^12.0.0"
  }
}`}>
`commander` is the argument-parsing library the CLI actually calls at runtime — every time `my-cli` runs, on every consumer's machine — so it belongs in `"dependencies"`, not `"devDependencies"`. Because npm skips `devDependencies` on a production install (`npm install --omit=dev`, or whenever a consumer installs this as a real dependency rather than cloning the repo), any consumer who installs this CLI normally gets `Cannot find module 'commander'` the moment they run it. The fix is moving it: `"dependencies": { "commander": "^12.0.0" }`.
</SpotTheBug>

<Callout title="The one-line takeaway">
A publish is effectively permanent, so every check in this lesson — `"files"`, `npm pack --dry-run`, `prepublishOnly`, 2FA, provenance — is designed to fail before `npm publish` uploads anything, because nothing meaningfully fixes a mistake after.
</Callout>
